Speaking a question

The member taps the mic, speaks, and reads back what was heard before anything is sent. Every state below is drawn for web and for the phone, because the same rules ship to both in the same session.

Three rules the whole design hangs on.
① Speak, then see. Not live word-by-word — a ten-second question does not benefit from a held-open connection, and both apps already work this way.
② The transcript is never auto-sent. A mis-heard trade term must be correctable before it spends one of the member's questions for the day.
③ Nobody picks a language before speaking. The server builds the candidate list from the member's app language, the business's country and the alphabets its own documents use. The picker exists only as a correction, after the fact.

03 The correction chip, precisely

This is the one piece of language UI in the whole feature, and it appears only after a transcript.

QuestionAnswer
When does it show?Only once a transcript exists. Never before speaking, and never as a gate.
What are the options?Exactly what the server said it chose from — the response carries the candidate list. The client never keeps a language list of its own.
How many?Whatever the server sent, capped there (default 4). One is already selected: the one that was heard.
What does a tap do?Re-sends the same recording forced to that one language. The member does not speak again.
Does it change the answer language?No. The answer is always in the language of the question. This only changes how the audio was read.
Is it ever pre-opened?No. Low confidence does not open it — that would tell every provider with an accent that something is wrong.
Why the chip is not optional. Measured on live Azure, 2026-09-02: Gurmukhi speech was identified as Hindi and written out in Devanagari — even with pa-IN in the candidate list. It did not fail; it produced readable, wrong-script text. For a Punjabi-speaking provider the chip is the only recovery that exists.

04 What this settles

The mic never sends anything

Speech only ever fills the field. Every path to an answer still goes through the member pressing Ask, so a mis-heard word costs nothing.

No number is hardcoded in a client

The recording cap, the size cap, the accepted formats and the language options are all delivered by the server. A client constant is how the copy and the rule drift apart.

Nobody picks a language to speak

The candidate list is built from what the server already knows. The only language control in the feature is a correction, after the fact.
