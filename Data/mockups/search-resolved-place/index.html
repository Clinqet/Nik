Which place we searched — the resolved-location chip

Customer web + phone. Type “London” and we pick one — London, Ontario or London, England — and never say which. From Phase 3 that choice also decides which country's index answers you, so picking the wrong one silently returns an entirely different country's providers. This chip says what we chose and lets it be changed in one tap. Eight states, drawn for approval; nothing is built.

Why this is not cosmetic. Before Phase 3 a mis-resolved city gave slightly-off results. After Phase 3 it routes the whole query to another country's index — and the customer has no way to tell that is what happened. The dangerous case is being confidently wrong, which is precisely the case a “show it only when ambiguous” design would hide. So the chip is always present whenever a location was used.
‼️ WHAT EXISTS TODAY: NOTHING. This is entirely new. Verified — there is no location indicator of any kind on the customer search results page. SearchBox.jsx uses a city only as hidden context for suggestions and never displays it. So a customer searching today has no way at all to see, or change, which place we searched. Where it goes: the customer search results page (app/(customer)/services/(search)/page.js), directly under the search bar and above the first result — and the same position in the phone app's search screen. The picker it opens is the existing location surface in each app (LocationPermissionModal.jsx on web, LocationPickerModal.tsx on phone), not a new one.
‼️ THE MARKER — corrected twice, 2026-09-22, both times after the owner looked at it. The first draft drew a ring in navy, which the owner read as black. It was wrong on two counts: the colour, and — more importantly — a circle says nothing about a place. The customer app already has the answer. AboutTab.jsx:236 renders FaMapMarkerAlt in text-[#97EF29]. So the marker here is a solid map pin in brand green #97EF29, the exact treatment the app already uses for a location — grey #B9BEC6 when nothing is set, amber #F5A623 when something needs attention. It is a plain map pin, not a decorative or AI-looking glyph. And the action. The first draft used #2F80ED, carried over from an older sheet — that blue is not in tailwind.config.js at all. The app has no raw blue. ‼️ Brand green cannot be used for text — a thin lime word on white is illegible — so the action is brand navy #032858, underlined, which is the app's own ink and reads unmistakably as a link. Green carries the icon; navy carries the words.

The last known place, stated as last-known. ‼️ Change is removed, not greyed — a control that cannot work should not be offered.
8 · ‼️ Routed to a different country than the device is in
Showing providers in Canada, near Niagara FallsChange
The border case. The customer is metres from another country, so the COUNTRY is named explicitly rather than implied. ‼️ This is a correct answer and must never be labelled degraded or uncertain.
‼️ State 8 gets its own wording for a reason. When the search crosses into the country-fan-out path the result is flagged internally as reduced-confidence. That flag must not reach this chip when the location itself was resolved cleanly — a correct answer displayed as broken teaches the customer to distrust a system that is working.

Responsive rules, binding. ‼️ The place name is never truncated to fit the action — below the breakpoint the action wraps to a second line, as drawn. The chip is one line wherever it fits and at most two lines ever; a very long place name ellipsises only the trailing part of the place, never the country. The chip is sticky with the search bar on web so it stays visible while scrolling results; on phone it scrolls away with the header. Tap target at least 44 px tall including the padding. No horizontal scrolling at any width. The picker is a centred dialog on web and a bottom sheet on phone, dismissed by swiping down.
