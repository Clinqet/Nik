You asked whether it should say “improve your AI assistant” or “the AI assistant”. Legally it must be “the Clinket AI assistant”, not “your assistant”. Improvements are platform-wide, not a private per-provider model. 2 · Two things I found — both now settled

① Recordings are hard-deleted at 90 days by an Azure Storage lifecycle rule — OUT OF SCOPE, your call azureautomation/storage.json deletes every blob under voice-recordings/ and voice-transcripts/ after voiceArtifactRetentionDays. It is a container-wide rule; it has no idea who consented. So “we’ll listen back to their recordings” only works inside that window.

Settled: not in scope (“don’t worry about it and we know it is internal only”). The shipped wording is safe either way — it never claims we keep consented recordings longer, only that they may be used to improve the assistant, which stays true if a longer-retention path is added later.
② A pre-ticked box is not valid “consent” — RESOLVED by design Pre-ticked boxes are explicitly invalid as GDPR consent (Planet49, C-673/17), and India’s DPDP Act wants a “clear affirmative action” too. Default-ON is the right product call — so it ships framed as what it actually is: a setting the provider can see and switch off, never a consent tick-box.

Why default-ON is defensible as built: it is never silently applied. The provider presses Finish setup / Save on a screen where the full statement is visible, so there is an affirmative act. It sits in its own row, separate from the existing mandatory “I authorize Clinket to answer calls…” consent, and it never blocks the button. Every grant and every withdrawal is evidenced permanently, so we can always demonstrate what was chosen and when.

5 · Behaviour rules — web and mobile identical

SituationWhat happens
Brand-new provider opens setupCheckbox is ON. Nothing is recorded as consent until they press Save draft or Finish setup — an abandoned screen grants nothing.
Provider returns to the Active screenCheckbox shows their saved value, every time. This is the “once I go back, that checkbox should always be there” requirement.
They save with no changeNothing. No alert, no consent record, no noise. Only a genuine OFF→ON or ON→OFF writes anything.
They tick it (OFF → ON)Timestamp stored · permanent consent record written · admin alert “AI training consent granted” (7-year, delete-blocked).
They untick it (ON → OFF)Timestamp cleared · permanent withdrawal record written · admin alert “AI training consent withdrawn” (7-year, delete-blocked). Withdrawal is logged just as permanently as the grant — that is the half people forget, and it is the half you get asked for.
Save failsNo alert, no consent record. Alerts are written only after the profile write commits, so we can never claim consent that was not saved.
Admin resolves the alertAllowed — but the retention is re-pinned to created + 7 years. Resolving cannot shorten it.
Admin tries to delete the alertBlocked by the API, and the delete button is hidden in the admin UI.
Provider cancels the assistantThe withdrawal record and the alerts survive. Cancelling the assistant does not erase the audit trail.
Assistant is paused / not yet activeRow still renders and still saves. It is a preference about data, not about call handling.

6 · What gets stored — approved and built

Three stores, three different jobs. This is the “TTL that never gets shortened” you asked for, and the answer to your WhatsApp question.

StoreWhatRetentionWhy
Cosmos — one new field on the existing voice application document trainingConsentAcceptedAt (nullable timestamp), sitting right beside the existing consentAcceptedAt Lives with the profile This is what makes the checkbox show the right value when they come back. A timestamp instead of a true/false gives us “when did they agree” for free, which is the first thing anyone asks. No new container, no new partition key, no index change.
User activity ledger — the existing consent ledger A VoiceTrainingConsent entry on every grant and every withdrawal Never expires (TTL −1) This is exactly what WhatsApp opt-in/opt-out already uses — you asked what we do for WhatsApp consent, and the answer is: it never expires, deliberately, and it is hard-coded so no config change can ever shorten it. Same list, same protection. This is the record that proves consent years later, and it is immune to the admin portal entirely — there is no button anywhere that can touch it.
Admin alert — the one you asked for One new alert type, VoiceTrainingConsentChanged, metadata says granted or withdrawn 2555 days = 7 years Written directly with its retention stamped on at creation — the same technique the existing “Provider verified” and “Admin access granted” governance alerts already use, precisely because a queued alert cannot carry its own retention and would silently get the 90-day default. Added to the immutable-audit list so resolve re-pins it to created + 7 years and delete is refused. That is your “resolving must not shorten the TTL” requirement, enforced server-side, not by convention.
Why both a never-expiring ledger entry and a 7-year alert, rather than one of them They answer different questions and have different threat models. The alert is the visible surface — it shows up in your existing Alerts page, filterable by type, which is the “see everyone who consented” view you want later, and it is where an admin actually looks. But alerts are an operational surface with a resolve button and (for ordinary types) a delete button, so it is the wrong place to keep the only copy of a legal fact. The ledger entry is the durable surface: never expires, no UI can delete it, per-provider. Belt and braces, and it costs one extra queued message per change — which happens maybe twice in a provider’s lifetime. The existing voice add-on consent already works exactly this way.
Not in this change — agreed ① No new admin page. The new alert type is filterable on the existing Alerts screen from day one; the dedicated “everyone who consented” view is a later, better-scoped piece of work. ② No change to how long recordings are kept (see finding ① above). ③ Nothing about call handling changes — the assistant behaves identically whether this is on or off.
