Report wrong answers

A visible, one-tap way for a provider to say "answers from this file are wrong". One tap sends one alert to the team, who look at that file's readings. Nothing else happens, and nothing is promised.

Replaces the rejected "tell our team" idea

01 · Why, in one paragraph

The provider never sees what we saved from their file. They only see the answers it produces, in Ask Clinket and on calls. When an answer is wrong, they need one obvious place to say so, right on the file, not inside the "…" menu. It is an error report, not feedback: no note box, no "our team", no reply promised. The confirmation says only what is true: it was reported, and we will check the file.

02 · The words — pick one

Recommended · W1

Report wrong answers

After the tap: Reported. We'll check this file.

Starts with what you do, so it reads as a button on a busy row. Three plain words; fits one phone line in all five languages. Screen readers hear the file name too.

W2

Wrong answers? Report it

After the tap: Reported. We'll check this file.

Friendly question form. Slightly longer, and a question is easier to read past on a row.

W3

This file gives wrong answers

After the tap: Reported. We'll check this file.

Closest to your own words, but it reads as a statement, not a button.

All frames below use W1.

03 · Web — the file list (laptop and iPad)

The control sits at the end of the file's own info line (pages · size · date), on every Ready file, for every member who can see the file. It is not behind the "…" menu and does not need the manage permission: anyone who saw a wrong answer can report it. It is a flag icon plus underlined navy text, the same style as the row's other links ("Show pictures", "Linked to …"). Every state replaces the text in place, so the row never jumps.

07 · Server rules (proposed — please confirm)

  • Who: any member of the business whose access lets them see this file (the same rule as the file list). Tenant-isolated: the file must belong to the caller's current business. No manage permission needed.
  • When: only a Ready file. Any other state is refused with a sentence the screen shows.
  • One alert per person, per file, per version, per day: the alert's id is derived from (business, file, version, member, UTC day). A double tap, a retry and a Service Bus redelivery all become the same single alert (the alert processor already de-duplicates by id). Superseded 2026-10-03 (owner ruling): nothing is stored; every tap is its own alert, bounded only by the per-member hourly limit (Voice:Knowledge:WrongAnswerReportsPerMemberPerHour, 10).
  • Rate limit: the API's existing per-user limiter, plus at most a small number of reports per member per hour across all files (a setting, not a constant).
  • Nothing else happens: no re-reading, no notice on the row, no email, no reply.
Your decision — "already reported" after the page reloads. Without a new stored field, the screen cannot know after a reload that you reported earlier today. A second tap then answers "Already reported today. We'll check this file." (A4), and no second alert is sent. Recommended: this, with no new field. The alternative is a stored "reported on" date per file and member, which is a §0.7 schema change. Superseded 2026-10-03 (owner ruling): nothing is stored and there is no "already reported" answer; after a reload the report is simply offered again.
