How this stays cheap

DecisionWhy
One identifier per call — user number, else email, else phone Mirrors lookupUser in userSupportService.js. Never sends all three, so the read stays a single indexed seek instead of a multi-column scan.
Explicit submit — no type-ahead A debounced lookup would multiply calls ~5–8× per search for no benefit: admins paste an identifier, they don't browse.
Resolve once, then reuse The resolved id fills the field; every existing action uses it directly. No re-resolution.
Business ID stays directly editable The deep-linked case (an alert naming the business) costs zero extra calls, and a resolver outage never blocks a repair.
Reuses existing indexes — no schema change Identifier→userId is the read /admin/users/lookup already does; userId→businesses seeks IX_BusinessMembership_User_Status on (UserId, Status), which already exists. No new table, column or index.
Capped result (10) with a count A person in many businesses can't fan out an unbounded list.
Shared BusinessLookupField component Payouts, Voice and WhatsApp admin all take a raw businessId today. One component means they can adopt it later without duplicating the resolver.
Needs your approval before any code: one new admin endpoint — GET /admin/providers/lookup?userNumber=|email=|phoneNumber= → the businesses that person belongs to (id, name, status). No schema change. Everything else is UI in SearchOperationsPanel.jsx plus one service function.
