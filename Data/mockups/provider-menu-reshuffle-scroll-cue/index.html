2 · Scroll cue — five options, live

Needs your pick

Drag the height down until the rail overflows and the cues appear; drag it back up and they all vanish. That is the “only when there is scroll” requirement, working.

560 px

Every option shares the same four rules. It renders only on measured overflow (scrollHeight − clientHeight > 1, re-measured on container resize and content change, mirroring the existing useHorizontalOverflow hook). It appears at the top edge too once you have scrolled down, so it says which way there is more. It never intercepts a click. And it drops its motion under prefers-reduced-motion.

You have already ruled on this once. global.css line 342 carries your own note: “Chip strips that overflow at phone/tablet widths keep a THIN brand scrollbar — an invisible scroller hides half the filters with no hint they exist (owner, 2026-08-13, the activity chips).” The Profile menu you circled follows it (bookings-table-scroll, navy 5 px thumb) — which is exactly why that menu does show a bar. The dashboard rail is the single surface that opted out, with sidebar-scroll-hidden. So the visible thin bar is not a new idea; it is the house rule, and the rail is the exception. It only has to be lime here, because a navy thumb on a navy rail is invisible — and .sidebar-scroll with a lime thumb is already written in global.css and used by nothing.

Why the bar alone (B) is not enough. On macOS, iPadOS and iOS Safari the browser hides overlay scrollbars until a scroll gesture has already started — so on exactly the iPad and laptop you described, B draws nothing until the user has already discovered the scroll by accident. The chip strips get away with it because their content is visibly clipped mid-chip; a rail clips cleanly between rows and looks finished.

C is chosen, and E is rejected on brand grounds. Lime means “this row is selected” on this rail — the active row is a solid lime pill. E’s “+N more” is a second solid lime chip that is not selectable, which is the confusion the brand rule exists to prevent. C’s chevron is a thin lime glyph, so it reads as an arrow, not a control. E also needs a localized plural string in five catalogues and a count that must stay correct while scrolling; C has no text at all.

Recorded difference: C drops the visible scrollbar, so it does not literally follow the chip-strip rule at global.css:342. It meets that rule’s intent — never hide the fact that content overflows — with a mechanism suited to a rail that clips cleanly between rows. If position and length ever matter, the answer is to add the thin lime bar back (that is option A), not to move to E.

4 · Mobile app — rethought from scratch

Needs your pick

You are right that the web Profile menu cannot be copied — it has no Team, no Billing, no Activity, no Refund Requests. Those live in the web rail, and mobile has no rail. So I stopped trying to mirror a screen and looked instead at where every destination can actually be reached on a phone today.

DestinationReachable on mobile fromVerdict
Dashboard · Bookings · Leads · InboxBottom tabFine — one tap, always visible
Quotes · Customers · Calendar · Invoices or Insights · Call Follow-ups FAB arc and the Profile listFine — the FAB is the shortcut
Address · Service Area · Category · Services & Price · Availability · Licence · Portfolio · Reviews · Offers · Voice Assistant Profile list onlyFine — setup, opened rarely, and a literal match for the web Profile menu you circled
Team · Activity · Refund Requests · Plan & Billing · Payment Settings Profile list only This is the actual problem. No tab, no FAB, and they sit in the middle of a 21-row list that opens with Plan & Billing and closes with Calendar

So the biggest value on mobile is not “put the five rows in the same order as web”. It is: break the 21-row block into four headed groups, each answering one question. Same rows, same names, same permission and flag gates, same destinations — just findable.

Group order is yours, and here is the trade-off in one line. Your business leads, so the ten setup rows sit above the day-to-day ones. The argument for it: somebody who tapped Profile most likely came for exactly those rows, and it makes the screen open with a literal match of the web menu. The argument against: those are the rows a settled provider opens least. Your call, applied as asked.

Smallest diff: the five agreed rows go to the top of the one existing block, everything else keeps its current sequence. No new headings, no new localization keys. Still a 21-row scan.

One divergence you should sign off knowingly. Web keeps Payment Settings under Profile → Account Management. Pairing it with Refund Requests in a mobile Payments group is a deliberate mobile-specific choice, not a mirror of web. It is defensible — both rows are the customer-money side of the product, and both hang off the online-booking-pay packages — but the two apps will now file that row differently, and I will record it as an owner decision rather than let it read as drift.

The Payments group is doubly conditional. Payment Settings is gated on payments.billingUiEnabled; Refund Requests on payments.onlineBookingPayEnabled and shows("refundRequests"). With both off the group vanishes heading and all — which is the correct behaviour, and the reason the heading can never be hardcoded above the rows.

A group whose rows are all hidden must render no heading. Every row keeps the gate it has today — shows("team"), payments.billingUiEnabled, payments.onlineBookingPayEnabled, payments.smartAnalyticsEnabled, payments.aiAssistantEnabled. A Technician on a Free plan would otherwise see an empty “Team & plan” heading, which is worse than no group at all.

Three things I considered and did NOT propose, because each is a separate decision rather than part of a reshuffle: a “More” bottom tab (the FAB already owns that slot and is an approved design); search inside the menu (genuinely useful at 21 rows, but it is a new control with its own empty and no-match states and deserves its own mockup); and surfacing Team / Refund Requests on the mobile dashboard home (a better answer to “hard to find” than any menu order, and worth doing — separately).

Three mobile/web differences I am deliberately NOT “fixing”, because each is correct as it stands: Appearance and Language are mobile-only (web puts the language picker in the rail header and follows the OS theme); Do not sell or share my data is mobile-only under Legal and is a CCPA-style in-app requirement; Data Deletion sits under Legal on mobile but Support on web — moving it is churn with an App Store reachability rule attached, so I would leave it and record the divergence.

Option 1 needs four headings in five catalogues (en-US · fr-CA · hi-IN · gu-IN · es-US, identical key sets): Your business · Team & plan · Work · Payments. Three are new; Your business can reuse the existing PROFILE_SCREEN.BUSINESS_MANAGEMENT string instead if you would rather not add a key — say which you prefer.

5 · Customer web + customer app

Needs your pick

I checked both. Short answer: the customer apps need the scroll cue for the same reason, need a much smaller order change, and have a naming problem that is worse than the provider one. The customer mobile app mirrors customer web row for row, order for order, label for label — I verified each one — so every decision below applies to both at once. There is no separate mobile choice to make here.

5.1 · Scroll cue — yes, the same defect

accountSidebarLayout.jsx line 204 renders the desktop account sidebar as sticky top-5 max-h-[calc(100vh-40px)] overflow-y-auto no-scrollbar. That is a capped-height scroll container with the scrollbar deliberately suppressed — the identical defect to the provider rail, on 20 rows across three groups plus headings. It will overflow on any laptop.

The cue inverts for this surface. The provider rail is navy, so it takes a navy fade and a lime chevron. The customer sidebar is a white panel on white, so it takes a white fade and a navy chevron — lime on white at 18 px would fail contrast, and navy is already the brand’s colour for this kind of mark. Same option C, same measured-overflow rule, mirrored palette.

My recommendation: drop “My” from every row, and this settles the provider question too. The group heading is literally “My Account”. Every “My” beneath it says the same word twice. Five of the eight rows already do it this way — the “My” rows are the minority, not the standard. That gives one rule for the whole product rather than two: ownership is established by the context, never repeated on the row. On the provider rail the context is the dashboard itself; here it is the group heading. Same rule, both apps.

“My invoices” is a bug either way. Whatever you decide about “My”, that lowercase i sitting two rows under “My Bookings” should be fixed in this change.

A pattern already solved here that provider mobile should copy. useVisibleNavGroups in accountSidebarNav.js already ends with .filter((group) => group.items.length > 0) — a group whose every row is flag-hidden renders no heading. That is exactly the rule I said the new provider-mobile groups need. Same idea, not a new invention.

One thing I would leave alone: Manage Addresses → Addresses is the only row above where I am less sure. “Manage” is the only imperative in the list, but it is also the only row that is purely an editing surface. Say the word if you would rather keep it.
