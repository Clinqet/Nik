## 3. Data placement and cost

**FOR EVERY COSMOS CHANGE, CHOOSE DELIBERATELY BETWEEN AN EXISTING CONTAINER AND A NEW ONE. READ THE ACTUAL CONTAINER DEFINITIONS, PARTITION KEYS, INDEXES, RETENTION AND THROUGHPUT CONFIGURATION. COMPARE THE CANDIDATE EXISTING CONTAINERS AND PICK THE ONE THAT FITS OWNERSHIP, ACCESS PATTERNS, RETENTION AND THE LOWEST SUSTAINABLE READ/WRITE RU COST. NEVER FORCE DATA INTO AN ILL-FITTING CONTAINER TO AVOID A JUSTIFIED NEW ONE.**

**THE OWNER'S CAPACITY CONCERN IS THAT ANOTHER CONTAINER CAN COMPETE FOR THE AVAILABLE PROVISIONED THROUGHPUT. VERIFY WHETHER THIS DATABASE USES SHARED DATABASE THROUGHPUT OR DEDICATED CONTAINER THROUGHPUT, INCLUDING ANY AUTOSCALE/MINIMUM EFFECTS; DO NOT ASSUME CAPACITY IS ALWAYS DIVIDED EQUALLY OR THAT A NEW CONTAINER IS FREE. RECORD THE ACTUAL CAPACITY/COST IMPLICATIONS, EXPECTED QUERY SHAPE, PARTITION HOTSPOTS, INDEX WRITE COST AND STORAGE/RETENTION IMPACT. USE CURRENT OFFICIAL DOCUMENTATION WHEN THE BEHAVIOR IS UNCERTAIN.**

**PREFER POINT READS AND BOUNDED PARTITION-SCOPED QUERIES; NEVER CROSS-PARTITION COSMOS QUERIES. USE ATOMIC UPDATES AND CONCURRENCY CONTROLS WHERE REQUIRED. A ONE-TO-ONE FACT GENERALLY BELONGS ON THE EXISTING ENTITY; FIXED VALUE SETS BELONG IN ENUMS. DO NOT ADD A DOCUMENT/TABLE FOR A CONSTANT. EVERY NEW STORED FACT MUST HAVE A CURRENT CONSUMER AND APPROPRIATE DELETION/RETENTION.**

Record the decision in PLAN §0.5 as **implemented under owner delegation AUT-1**, not as an invented per-item owner reply. Test migrations and real database behavior.
