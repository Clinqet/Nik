  ask for feedback, deliver a notice, collect information, promote an offer to people who consented).
- **Individual AI calls** — one shared "Call with AI" form from AI Calls/Calls, either dashboard, Contacts/profile, a booking or Call Follow-up. Select one person or a bounded small group, enter a shared goal and choose now or later. Create a separate `OneOff` recipient call for each eligible number, with independent result/history/cancel; a shared immutable brief may be reused. **No visible or hidden campaign is created. Booking entry stays locked to its original customer.** See §18.7 and QUICK-CALLS.md.
- **Callbacks** — on any AI call (inbound or outbound) the person asks to be called at a time; the AI checks the
  allowed hours, books it, and the engine calls back on time.

The AI on the call is the **existing** assistant stack: Azure realtime models, the MCP tool server
(`clinqetmcp/Clinqet.Mcp`), provider knowledge, existing sending tools, existing post-call pipeline — with an
outbound brief and new tools. The carrier places the call; the AI joins the answered leg (Azure/OpenAI cannot
originate outbound calls).

Every call type goes live in the code. **A call only goes out when the evidence it needs exists** (consent
record, declared Indian number, allowed number series, minutes, permission). Missing evidence means the screen
says exactly what is missing and nothing dials. This is not a feature flag (owner rule: no feature flags).

## §4 Core model

### §4.1 Relationships

```
Business ─┬─ Brief (templates or one-off) ── BriefVersion (frozen when used)
          ├─ Campaign ── BriefVersion ── RecipientCall* ── Attempt* ── Answer*
          ├─ RecipientCall (Kind = OneOff | Callback | Test) ── Attempt* ── Answer*
          └─ Contact permissions (per E.164)          Platform contact permissions (per E.164)
```

### §4.2 Campaign states

`Draft` → `Scheduled` (launched, start in future) → `Running` ⇄ `Paused(reason)` → `Completed` | `Cancelled`

- Pause reasons: `ByMember`, `MinutesExhausted`, `MinuteCapReached`, `Safety` (auto-pause, §19), `Admin`.
- `Completed` when every recipient call is terminal. `Cancelled` stops future work; active calls end politely.
- Editing a `Running`/`Paused` campaign creates a new brief version, used only by recipient calls with no attempt yet.

### §4.3 Recipient call states and outcomes

States: `Waiting` · `Dialing` · `InConversation` · `Unknown` · `Done` · `Blocked` · `Exhausted` · `Cancelled` · `Expired`

Outcomes: `Completed` · `Partial` · `Declined` · `OptedOut` · `WrongPerson` · `InvalidNumber` · `VoicemailLeft` ·
`NoAnswer` · `HungUpEarly` · `NeedsFollowUp` · `TechnicalFailure` · `Blocked(reason)` · `Expired` · `Cancelled`.
A callback booked on a call creates or reschedules work (see §8).

### §4.4 Attempt states

`Claimed` → `Dispatched` → `Dialing` → `Ringing` → `Answered(Human|Machine|Screening|Unknown)` → `InConversation` → `Ended`,
or `NoAnswer` · `Busy` · `Rejected` · `Failed` · `Unknown` (carrier outcome not known — reconciled, never redialed).
Each attempt has its **own call id** (summary id, recording file name and queue duplicate-detection all key on it).

## §5 The brief

| Field | Rules | Default |
|---|---|---|
| Purpose | `Service` (appointment reminder/confirmation · follow-up · feedback · information notice · collect information · custom service) or `Promotional`. `RequestedCallback` is set by the system | From template |
| Goal + "done when" | One sentence each; bounded length (settings) | From template |
| Points to say | Up to 5 short points the AI must deliver | None |
| Questions | Typed: yes/no, choice, number, date/time, rating 1–5, short text; required/optional; bounded count (setting) | None |
| Allowed actions | Book/reschedule/cancel appointment (existing booking tools) · send details (existing tools) · send a handout (D9) · ask the team to follow up | From template |
| Documents | `All` (every document the assistant uses) or `Selected` (subset, bounded — setting, suggested 50) | All |
| Voicemail | `LeaveShortMessage` or `None` | Leave, at most once |
| Call length | Target and hard limit | 2 min target, 5 min limit, max 10 (settings) |
| Language | Call language; the AI follows the person into another supported voice language (en, fr, es, hi, pa, gu) | Business language |
| Extra instructions | Free text, length-limited like standing instructions | None |
| Linked booking (optional) | For reminders/confirmations; the dial check verifies the booking is still valid | None |

- **AI drafting:** the provider types one sentence; the AI fills the brief; the provider edits before launch.
- **Narrow only:** a brief can restrict documents, actions and tools; it can never enable anything the business has
  not allowed. The business's standing instructions still apply to outbound calls; verification and privacy rules
  are never overridable.
- **Promotional briefs** require consent evidence per person (§9, §10). The provider confirms "this call does not
  sell or promote anything" for Service briefs; the AI is instructed not to pitch on service calls.
- Validation before launch: contradictions (two prices, expired offers), empty required parts, knowledge selection
  that resolves to nothing usable, handouts not approved.

## §6 How one call works

### §6.1 Steps

1. **Due.** A recipient call's `NextAttemptAt` arrives; it is always inside the allowed window (§8.4).
2. **Claimed fairly** by the scheduler (§13): one bounded SQL selection across all businesses; in one transaction
   per business (app-lock): create the attempt, hold minutes (§14), check campaign cap, mark the recipient call
   `Dialing`. Dispatch through the outbox (§13.3).
3. **Final checks right before dialing — all fail closed:**
   - business has an active AI Assistant, not on hold; campaign still running (campaign kind);
   - attempt still `Claimed`, recipient call still `Dialing` (row version);
   - contact still exists and its number equals the scheduled number (never silently call a new number);
   - linked booking still valid (not cancelled, start in future);
   - contact permissions: business scope and platform scope (Cosmos point reads); a failed read means no dial;
   - purpose evidence: promotional → valid consent; India → caller number declared and of an allowed series;
   - local time inside the window; frequency limits (§8.3); capacity (§13.5);
   - destination rules: E.164 valid; not emergency/short/premium; not a Clinket number; country allowed;
     non-production allow-list (§16).
4. **Live call record.** Write the Cosmos live call record (existing `vcall_{callId}` family, outbound fields
   approved in Phase 2) with the frozen brief, recipient facts, allowed documents and tools. The AI never needs SQL.
5. **Dial from the business's own Clinket number** with the business name, machine detection on, a time limit,
   and the attempt id in the carrier correlation field. Unknown carrier result → `Unknown`, reconcile, never redial.
6. **Detection** (§6.3).
7. **At answer:** re-read contact permissions. If blocked in the meantime: a brief "Sorry for the call, goodbye"
   and hang up.
8. **Conversation** (§7).
9. **After the call** (§6.5).

### §6.2 Carriers

| | Canada/US — Telnyx | India — Plivo |
|---|---|---|
| Dial | Standalone make-call (`POST v2/calls`, no `link_to`) — extend the existing `IVoiceTelephonyProvider.MakeCallAsync` used by the own-number check | Make-a-Call API — the existing `IPlivoMultipartyCallService.MakeProviderCallAsync` shape; the shared `MakeCallAsync`/`DialAsync` are **no-ops on Plivo** |
| Correlation | `client_state` with an `outbound` phase + attempt id, routed **before** the inbound state machine (as the own-number check does) | Dedicated outbound callback routes with `?attemptId=` (as the own-number check does); `request_uuid` → CallUUID via callbacks |
| Duplicate safety | Deterministic `command_id` per attempt. It is derived from `(leg/to, action, client_state)`, so a deliberate retry needs a new attempt id in `client_state` | **No idempotency key; the adapter retries the POST on 429/5xx.** Outbound must dial each attempt once: a 5xx/timeout after send is `Unknown`, reconciled, never re-sent |
| Machine detection | Premium AMD with iPhone call-screening detection (existing mode) | Plain async `machine_detection` (verdict can be wrong; empty verdict counts as human today) |
| AI join | On a person: transfer the answered leg to Azure realtime SIP with the per-call token header; the existing accept webhook takes over (session must be in `AiHandoff`) | On answer: applet joins a named conference (MPC); add the AI as an `ai-agent` member through the existing WSS relay in the MCP host |
| Caller ID | The business's Telnyx-owned Clinket DID (STIR/SHAKEN "A"); `from_display_name` = business name | Plivo-rented Indian DID (DoT rule) |
| Callback URLs | — | Queue-started dials need `Plivo:CallbackBaseUrl` (empty in committed config; set by `deploy.ps1`) |

**Never use `+18449254651`** as an outbound caller ID: it is the platform SMS sender and the CA/US own-number
verification caller, and its area code 844 is on `Telnyx:FraudDetection:HighRiskAreaCodes`.

### §6.3 Detection outcomes

| Result | Action |
|---|---|
| Person (`human_residence`, `human_business`) | Connect the AI; re-check permissions; opening (§7.1) |
| Machine | Wait for the beep (Telnyx `call.machine.premium.greeting.ended` — **not mapped today in `TelnyxWebhookParser`, must be added**; Plivo: an applet that waits for the beep). If voicemail allowed and not yet left: speak the fixed voicemail text (carrier TTS), hang up, outcome `VoicemailLeft`. Otherwise hang up. |
| Call screening (iPhone/Pixel) | Speak the fixed short "who is calling and why" line; wait for the person or the screening result |
| Unsure / silence | Connect the AI (cautious). If the AI hears a voicemail greeting it waits for the tone, speaks the exact voicemail text if allowed and not yet left, and ends |
| Fax | Stop voice calls to that number (`InvalidNumber` for voice) |
| No answer / busy / rejected / failed | Attempt ends; next step per §8 |

**Measured, not guessed (Phase 2):** the silence a person hears after "Hello?" decides whether they stay. Phase 2
measures two options on real calls — (a) detection first, then connect the AI; (b) connect the AI on answer with
detection running alongside, the AI waiting for the person to speak and being cut on a machine verdict — and
**shows the owner the numbers before choosing.**

### §6.4 Test calls

"Call me to test": dials the member's own **verified** phone (from Identity), uses the brief, free (usage recorded
with source `Test`, never charged), 5 a day per business (setting), never counted in campaign results.

### §6.5 After the call

In order, idempotent per attempt:
1. Record usage from the carrier's answer and hang-up times into the SQL ledger (§14) and settle the hold —
   **before and independent of the summary** (today a summary-model failure loses metering; not acceptable here).
2. Finalize answers and the outcome in SQL (the AI's declared outcome, checked by the post-call classifier).
3. Decide the next step (§8): retry, callback, done.
4. Summary + transcript + recording through the existing post-call pipeline, with the outbound path.
5. Post-call safety check: if the transcript shows a missed "stop calling me", record do-not-call (source
   `SafetyCheck`) and raise an admin alert.
6. Campaign counters, restrained notifications (§20), analytics events, activity rows.

## §7 The conversation

### §7.1 Opening (fixed text, translated, compliance-critical)

Order: greeting · "this is the AI assistant for {Business}" · "calling for {First name} about {purpose}" ·
"Is this {First name}?" — then, once the right person is confirmed: "Just so you know, this call is recorded."
(recording notice only when the business records calls).

- **AI disclosure is always on** (Microsoft and OpenAI usage terms; CRTC consultation 2026-132; US state laws).
- A callback number and the business's email or postal address are given on request (Canada automated-call rule).
- No carrier-played preamble before the AI (it makes people hang up); the AI speaks the notice itself.
- Recording starts after the opening so no one is recorded before being told.
- The exact opening, voicemail and screening lines come from localization resources (not model improvisation),
  for every voice language; `pa` falls back like the existing disclaimer does. Phase 2 confirms the mechanism.

### §7.2 Behaviour

| Situation | The AI | Outcome |
|---|---|---|
| Wrong person / household member / child | No details; offers a message with the business name only, or a better time | `WrongPerson` (stop for that number unless the provider corrects it) |
| Personal details needed (clinic, insurance, finance) | Verifies first with the existing one-time-code tools when the brief requires it | Verification failed → no details |
| "Not a good time" | Offers a callback inside the allowed hours; books it | Callback |
| "Not interested" | Thanks them and ends; no persuasion | `Declined`, no retries |
| "Stop calling me" (any wording) | Records do-not-call **first**, confirms only after the save succeeds, ends politely | `OptedOut` |
| "Never contact me at all" | Same, scope all contact from this business (also mutes WhatsApp from that business) | `OptedOut` |
| Question it can't answer | Says so; offers a follow-up from the team | `NeedsFollowUp` |
| Wants a person | Offers a call back from the team (live transfer is a later project) | `NeedsFollowUp` |
| Medical, legal, financial, insurance advice | Declines politely; offers the team | `NeedsFollowUp` |
| Silence | Two gentle checks, then a polite close (existing watchdogs, outbound wording) | By result |
| Hostile | Calm; offers to end; a clear stop becomes do-not-call | `Declined` / `OptedOut` |
| 60 s before the limit | Wraps up; offers a callback if the goal isn't done | `Partial` / callback |
| Another supported language | Switches; otherwise offers a follow-up | By result |
| Document text or contact fields contain instructions | Treated as data; tools and limits are server-enforced | — |

### §7.3 Tools (server-bound; the model never supplies business, contact, document or call ids that the server trusts)

New:
- `record_answer(question, value, status)` — typed, validated against the brief; unclear answers stored
  unconfirmed, never guessed.
- `schedule_callback(local date/time)` — checked against the calling window and the person's time zone;
  **saved durably before the AI confirms**. The MCP host has no SQL. A precedent for an MCP → Main API call exists:
  `VoiceLiveEventClient` posts to `/api/v1/internal/voice/live-event` with `X-Internal-Api-Key` (10-second timeout).
  Phase 2 proposes the durable path (a new internal authenticated endpoint on that pattern, or a Service Bus message
  processed into SQL) with a recommendation. If the save fails the AI does not promise a time, and the post-call step
  retries from the live record.
- `record_do_not_call(scope)` — written directly to the contact-permissions store **before** the AI confirms.
- `set_outcome(result, note)` — the AI declares success, partial, declined, etc.; the post-call step checks it.

Existing tools stay available, filtered by the brief's allowed actions (booking tools, send details/material,
one-time codes, `end_call`). Knowledge tools honour the brief's document narrowing (§15.2).

Inbound AI calls also get: `record_do_not_call`, `schedule_callback` (callbacks from inbound calls), the neutral
recent-outbound note (D14), and in Phase 3 the promotional-consent question (§9.6).

### §7.4 Prompt

A dedicated outbound branch of `RealtimeSessionPayloadBuilder` (both the Telnyx accept path in Functions and the
Plivo relay in the MCP host build it — they must behave the same). Inbound wording that must not leak into
outbound: "answering its phone", "the owner's phone was rung", "how can I help you?", "follow the caller's lead",
"the owner is not available", "thanks for calling / call back anytime" (farewell phrases and idle goodbye).

## §8 Outcomes, retries, frequency and calling windows

### §8.1 Next step by outcome

| What happened | Counts toward limits? | Next step |
|---|---|---|
| No answer, busy, rejected, screening without pickup | Yes | Retry ≥ 1 day later at a different time of day |
| Voicemail | Yes | Leave one message the first time only; retry if the goal needs a conversation; stop if a message was enough |
| Answered, hung up within ~10 s | Yes | **No automatic retry**; the provider may retry manually |
| Conversation dropped (network) before the goal | Yes | One retry after 15 minutes if the person agreed to continue; otherwise `Partial` |
| Our own failure before anyone spoke | **No** | Retry after 15 minutes, at most twice, then alert |
| Callback requested | Yes | Call at that time; one retry 15 minutes later if unanswered; replaces the normal schedule |
| Goal done, declined, opted out, wrong person, invalid number | Yes | Stop |
| An action's result unknown (e.g. booking timed out) | — | Reconcile the action first; never repeat blindly |
| Dial result unknown | — | Reconcile; never redial the same attempt |

### §8.2 Limits (D11; settings, adjustable only within platform bounds)

- 3 calls in total per recipient call (first call + 2 retries).
- At least one day apart, at a different time of day each time (e.g. morning, then afternoon).
- At most 1 voicemail per recipient call.
- No automatic retry after a hang-up.
- At most 3 calls a week to one number from one business, across all its campaigns and one-off calls.
- At most 3 AI calls a day to one number across all businesses (silently deferred; no business sees another's).
- A callback the person asked for is not held to the one-day gap.
- A recipient call expires 7 days after its first attempt, or at the brief's "not after" time (e.g. appointment start).
- Minimum gap between any two calls to the same number: 1 hour (except a requested callback) — also closes the
  replication window for opt-outs (§9.8).

### §8.3 Frequency and destination guard

- **One active call per number, platform-wide** (enforced by a SQL unique rule over active attempts).
- Frequency counts come from SQL attempts per `(business, number)` and per number.

### §8.4 Calling windows

| Country | Legal envelope used by the engine |
|---|---|
| Canada | Weekdays 9:00–21:30, weekends 10:00–18:00 (automated/telemarketing rules) |
| US | 8:00–21:00 local; 8:00–20:00 and ≤ 3 calls per 24 h on one subject in FL, OK (and similar states — Phase 1 encodes the state list after the US legal review; until then use the stricter 8:00–20:00 everywhere in the US) |
| India | No statutory hours found; respect the person's time-band preference where known; default brief window applies |

Default brief window (D12): Mon–Fri 9:00–19:00, Sat 10:00–16:00, no Sundays. Effective window = legal envelope ∩
brief window ∩ (optionally) business opening hours.

**Time zone of the person:** contact address → zone; otherwise the phone's area code (NANP), using only hours
allowed in every zone of a multi-zone code; India = IST. **Unknown → hold the recipient call as "time zone
unknown"; never guess.** Daylight-saving: store local time + zone for callbacks; resolve to UTC at dial time.

## §9 Contact permissions: do-not-call and consent

### §9.1 Principles

- **Keyed by phone number (E.164), never a flag on the contact.** Contacts are hard-deleted and re-created with new
  ids; formats vary today; imports and edits would overwrite a flag.
- Many ways to add; one narrow way to remove.
- Checked at every step; written before the AI says "done"; full history kept.
- One authoritative store (Cosmos), reachable from every host including the MCP tool server (which has no SQL).

### §9.2 Scopes

| Scope | Set by | Meaning |
|---|---|---|
| This business — calls | The person on any AI call ("stop calling me"); the provider ("block calls"); the safety check | No AI calls from this business |
| This business — all contact | The person ("never contact me at all") | No AI calls + WhatsApp from this business muted (existing per-business mute) |
| Every business on Clinket | Admin (abuse), or an explicit request through a future public opt-out page | No AI calls from any business |
| "Don't call me about this again" | The person | Stops that recipient call only; not a do-not-call entry |

### §9.3 Removal

- A request the **person** made: only the person can lift it — e.g. they call the business and clearly confirm
  "you can call me again" (inbound AI records it with evidence), or a verified page later. The provider cannot.
- A block the **provider** added: the provider may remove it (`outbound.contacts.manage`, live-checked), recorded.
- Platform entries: admin only, recorded.

### §9.4 Enforcement points

| Where | How |
|---|---|
| Choosing people | One partition read of the business's entries; blocked people excluded and counted on screen |
| Scheduling | When a number becomes blocked, its pending recipient calls are cancelled (message to the control plane) |
| Right before dialing | Point reads, business + platform; failed read = no dial |
| At answer | Read again; blocked → brief apology, hang up |
| During any call | Tool writes immediately; the AI confirms only after the save succeeds |
| After the call | Transcript safety check; a missed request is recorded + admin alert |
| Screens | Contact, campaign and call views show the status, date and source |

### §9.5 History and retention

Every change is an appended event (who/what/when/why/evidence). Retention per §21: kept while the business exists,
and 5 years after the last change even if the business closes (number, dates, scope, proof only).

**AUT-1 research instruction:** the owner asked implementers to reassess the lowest-friction lawful consent flow. Follow IMPLEMENTATION-CHARTER.md §4 before changing eligibility or evidence requirements. The current rules below remain the baseline until a researched decision and matching implementation/tests replace them; provider attestation, automatic-consent or liability-disclaimer ideas are not adopted by this documentation update.

### §9.6 Consent for promotional calls (Phase 3) — five ways (F2)

| Way | How it works | Valid for |
|---|---|---|
| Consent link | The business sends a Clinket consent page by WhatsApp or email; the customer types their name, ticks the box, confirms the phone with a one-time code; we store the exact wording (version), time, language as signed consent | Canada, US |
| Checkbox when booking | Optional, unticked box on the Clinket customer app (web + mobile) and the business's public page: "I'd like {business} to call me about offers. Calls may use an AI assistant." | Canada; US when signed in with a verified phone |
| On an incoming AI call | The AI may ask "Would you like {business} to call you about offers?" Canada: the recorded yes counts (recording must be on). US: the AI sends the consent link to confirm in writing | Canada (recorded); US through the link |
| Upload a signed paper form | For consent collected on paper; image stored as evidence; uploader recorded | Canada only |
| Operator consent (India) | Consent through the telecom operator's consent system; Clinket stores the reference. Until that connection exists, India promotional calls cannot go out and the screen says why | India |

A "stop" always wins over consent. Consent expires per country rules and can be withdrawn on any call or on the same
page. Provider attestation alone is **never** accepted for promotional calls.

### §9.7 SMS STOP and keypad

- Business numbers are bought **voice-only** (no messaging profile), so "reply STOP" to a business number is not
  possible; never tell people to "reply STOP". India SMS is OTP-only.
- An SMS STOP today changes preferences only for platform accounts; a number without an account stores nothing
  (owner decision DR-3, recorded in memory). Not changed by this programme unless the owner asks.
- There is no keypad (DTMF) handling in voice today; voice opt-out works by saying it. A keypad option would be new
  work (US telemarketing may need it — confirm in the US legal review).

### §9.8 Why no race can slip through

- One active call per number platform-wide + 1-hour minimum gap between calls to one number: an opt-out on one call
  is saved before any other call to that number can start (Cosmos replication lag is milliseconds).
- The answer-time re-check covers the ringing seconds.
- A failed save means the AI does not confirm; the post-call step retries from the live record.

## §11 Architecture and sources of truth

### §11.1 One home per fact

| Fact | The one home that decides | Copies (never decide) |
|---|---|---|
| Briefs, campaigns, recipient calls, attempts, schedule, answers, outcomes | **SQL** (the shared `AppDbContext`, per region) | Frozen brief copy on the live call record, for that call only |
| Minutes: grants, usage, holds | **SQL ledger** | `Voiceline` monthly cap/usage fields: a projection for the inbound call-start check and display |
| Do-not-call and consent | **Cosmos** (one document family, append-only history) | None; screens read live |
| What happens during a live call | **Cosmos live call record** (temporary; outbound kept 24 h) | Moves into SQL after the call; from then SQL decides |
| Recordings, transcripts, handouts, consent evidence | **Blob** | — |
| Contacts | **Cosmos** (as today) | The recipient call keeps the scheduled name/number and re-checks before dialing |

### §11.2 Why SQL for the control plane

- Global, fair due-work selection across all businesses in one indexed query — Cosmos cannot do this without
  cross-partition queries, which are forbidden (CLAUDE.md §0.6).
- Claim + hold + budget in one transaction; unique rules make double calls and double charges impossible at the
  database level.
- The India Cosmos account is capped at 1,000 RU/s for the whole platform (free tier, provisioned); bulk campaign
  rosters there could slow everything in India.
- Precedents: billing charging engine (SQL + Service Bus fan-out + idempotency key before the external call);
  `AccessChangeDispatcher` (SQL outbox, per-minute sweep).
- Patterns: Microsoft Scheduler Agent Supervisor; transactional outbox; idempotent consumers; database-enforced
  invariants; OWASP Top 10 for LLM apps (LLM01, LLM06, LLM10).
- Accepted cost: departs from "Cosmos for operational data" (CLAUDE.md §3) by owner decision D3; SQL is S0 (10 DTU)
  in production and needs a tier review as volume grows (measure in Phase 2).

### §11.3 Why contact permissions live in Cosmos

The component that hears "stop calling me" is the MCP tool server, which has **no SQL by design** (voice skill:
"THE MCP HOST HAS NO SQL"). Writing straight to the one deciding store saves the opt-out before the AI confirms,
with no second service in between. Every dial and answer reads the same store.

### §11.4 Loophole check (each item must have a test)

| Risk | What closes it |
|---|---|
| Same person called twice at once | Unique active-call-per-number rule + 1-hour minimum gap |
| Message delivered twice / two workers | Attempt claimed once (row version + unique attempt number); carrier command id per attempt |
| Carrier timeout after possibly dialing | `Unknown` + reconcile; never redial |
| Dial lost between database and queue | Outbox + supervisor re-send |
| Opt-out races a new call | §9.8 |
| AI tricked into acting | Server-bound ids, narrow-only brief, per-call tool limits, permission checks per tool |
| One business sees another's data | Business id from the signed token on every query; cross-tenant tests |
| Change mid-flight | Everything re-checked right before dialing |
| Summary model fails | Outcome and usage recorded first, independently |
| Charged twice | One usage row per call id (unique) |
| Campaigns overspend together | Per-business lock + holds |

## §13 Scheduler, dispatch, supervisor and capacity

### §13.1 Scheduler (Functions timer, singleton)

- Every 15 seconds (setting). One bounded SQL selection of due recipient calls: `Waiting`, `NextAttemptAt ≤ now`,
  not expired; campaign `Running` where applicable.
- Priority: callbacks → one-off → campaigns; round-robin across businesses (per-business free slots).
- Free slots = business concurrency limit − its active attempts; region outbound ceiling − active outbound attempts.

### §13.2 Claim (per recipient call)

In one transaction with a per-business app lock (pattern: `sp_getapplock`, as billing does): re-check row version and
state → frequency limits → minutes available (§14.4) ≥ hold → insert attempt (`Claimed`) + hold → recipient call
`Dialing`, attempt count +1 → commit. Not enough minutes: campaign `Paused(MinutesExhausted)` / one-off
`Blocked(minutes)` + one notification.

### §13.3 Dispatch (outbox)

After commit, send `outbound-dial` message (message id = attempt id) and stamp `DispatchedAt`. The supervisor
re-sends claimed-but-undispatched attempts older than a threshold.

### §13.4 Supervisor (reconciliation sweep)

Stuck `Dialing`/`Unknown` attempts (reconcile via webhooks received or a carrier lookup), expired holds (release),
live records past their time, recipient calls whose next step was not written, retention clean-up (§21).

### §13.5 Capacity

| Limit | Default |
|---|---|
| Per business simultaneous outbound calls | 2 (F6; admin-adjustable) |
| Per campaign | ≤ business limit (setting) |
| Region outbound ceiling | Below realtime capacity so inbound always has room (setting; sized with Azure quota, §0.3 #6) |
| Telnyx dials per second | ≤ 30 (account limit) |
| Plivo India | 2 calls per second, 50 concurrent (hard enforced) |
| People per campaign | 5,000 (F6; admin-adjustable) |
| New business daily people | 100 (F1; admin-adjustable) |

Also: MCP tool rate limiter counts **per business** (4 concurrent, 60/min, in memory per instance) — change to
per call so a business running several calls does not throttle itself. Realtime `MaxConcurrentCalls` is only an
alert today — the scheduler's region ceiling is the real admission control. MCP runs as one P0v3 instance per
region with no autoscale — justify autoscale under AUT-1 (actual cost and capacity) and load-test in Phase 2.

### §13.6 New infrastructure (each with ARM + `deploy.ps1` + `ServiceBusSettings` list in the same change)

- Queue `outbound-dial` (dispatch). Post-call reuses `voice-postcall` with new kinds (40-minute duplicate window).
- A message path for "number blocked → cancel pending recipient calls" (a new queue or reuse — Phase 2 proposes).
- Timers: scheduler, supervisor (schedules via settings).
- MCP autoscale; realtime quota.

## §14 Billing and minutes

### §14.1 Today (verified 2026-09-25)

- Grants in SQL `MinuteLedger` (`IncludedGrant`, `TopUpPurchase`, `Adjustment`); cap = their sum for the UTC month;
  `IMinuteLedgerService.cs:3-5`: *"consumption stays in Voiceline.UsageSeconds"*. `Consumption`/`Expiry` entry
  types are never written.
- Usage: Cosmos `Voiceline.usageSeconds` per DID, best-effort atomic increment in the post-call processor, only when
  the summary is newly created; whole call from `call.initiated` (ring and disclaimer included) for every path except
  Missed; month = processing time. A summary-model failure loses metering.
- Gate: a snapshot at inbound call start (`IsCapExceeded`); no holds; no mid-call cutoff.
- Plans: AI add-on base minutes + plan bonus in the seeded catalog, admin-editable after seeding. **Unchanged by this
  programme (D22).**
- `MinuteLedgerService` also owns pack purchases, carry-over and the standard/advanced engine switch, all under the
  per-business app lock `minuteledger:{businessId}`; used minutes are read from
  `Voiceline.UsageSecondsForStable(period)`. Read it end to end before changing it — the separate top-up engine task
  (§24) touches the same service.

### §14.2 Target (D4)

- **One append-only SQL ledger:** grants (in), usage (out, per call, seconds), holds (pending). Corrections are
  adjustment rows; history is never edited.
- **Outbound billing:** per second from answer to hang-up; no answer / busy / failed free; voicemail message billed
  for its seconds; test calls free.
- **Inbound metering moves to the ledger too** (one balance needs one source of truth). The inbound call-start check
  keeps reading a `Voiceline` projection refreshed after every settlement and grant; the projection never decides
  money.
- Usage is written from carrier answer/hang-up events, not from the summary; a nightly reconciliation compares the
  ledger with the calls.
- Month = the call's own time.

### §14.3 Holds

Before every outbound dial: hold = the brief's hard limit (plus a small buffer); after the call: settle actual
seconds, release the rest; expired holds released by the supervisor. Inbound calls take no hold (unplanned); they are
covered by inbound protection; possible overshoot is at most one in-flight call, as today.

### §14.4 Availability for an outbound hold

`available = eligible grants for the period − usage − active holds − inbound protection`

- Outbound spends outbound-only credit (e.g. the trial grant) first, then shared credit.
- Inbound protection = 20% (setting) of the month's shared minutes, never usable by outbound.
- Campaign minute cap checked in the same transaction.

### §14.5 Trial, test calls, caps

- Outbound trial grant: once per business, outbound-only eligibility, amount and validity are settings (example 30
  minutes / 30 days).
- Test calls: 5 a day, free.
- Campaign minute cap: required; pre-filled from an estimate.
- Auto-recharge unchanged (runs after settlement); low/exhausted notices unchanged in wording but driven by the ledger.

### §14.6 Known billing risks (separate tasks already raised)

- Top-up packs are not engine-checked on the server (task raised; owner started it).
- Top-up prices were set for inbound margins; outbound adds carrier termination (~$0.002–0.005/min) and premium AMD
  ($0.0065/call) — owner to review prices (no change in this programme).

## §23 Existing-code coupling points (what must change)

The voice stack assumes every call is inbound. Verified coupling points:

1. Sessions are created only on an incoming `call.initiated` (`VoiceCallControlFunction`); Plivo only on the DID's
   `answer_url`. Outbound creates its live record before dialing.
2. Telnyx handlers look sessions up by `call_session_id`; a dial response returns `call_control_id`. Route outbound
   events by `client_state` (own-number-check precedent). Plivo make-call returns only `request_uuid`.
3. **The AMD handler never checks which leg a verdict is for** — an outbound leg's verdict would be read as "the
   provider missed the call". Route outbound first.
4. `Dnis` = "the number dialled" and `CallerPhone` = "who called" drive metering, known-caller lookup, caller-ID
   auto-verification (a number the business dialled is not proof of identity), send targets, CRM ensure, owner-rule
   and time-zone anchors. For outbound: `Dnis` = the business DID, `CallerPhone` = the person, with outbound semantics
   reviewed at every use.
5. Prompt, greeting, farewell phrases, idle goodbye, "owner unavailable" wording (§7.4).
6. `CallSummaryPath` has only `Whisperer`, `Receptionist`, `Voicemail`, `Missed`; an empty transcript reads
   "Missed call"; analytics map unknown paths to `call_missed`; the Call Follow-ups UI has 4 hard-coded tabs.
7. Metering starts at session creation and depends on the summary being created (§14.1).
8. AI-created bookings are stamped customer-initiated and customer-confirmed; outbound needs its own attribution.
9. WhatsApp auto-consent source `CustomerInitiated` (§15.4).
10. The caller-number fallback binding (`vcallani_{e164}`) is last-writer-wins; concurrent calls with the same number
    collide (the per-number rule prevents concurrency).
11. Plivo dial retries on 429/5xx with no idempotency (§6.2).
12. Live-call alert wording ("Clinket AI picked up a call from…") is noise for campaigns.
13. MCP tool limiter per business; realtime concurrency not enforced (§13.5).
14. One call id per attempt (summary id, recording name, `vpc-end-{callId}` duplicate detection).
