## Recommendation and alternatives

**Strong recommendation:** use the existing SystemData container (`/pk`) for a small regional carrier-account inventory, with number, business-slot, operation and daily-budget records in the same explicit partition. Use the existing ProviderData business profile and per-number runtime document as projections. Retain SQL as billing authority. Do not create a SQL inventory table or another Cosmos container.

The partition key is a configured opaque inventory-scope ID, unique to deployment and carrier account; never derive it from a secret. Its exact value must be approved before provisioning. Every inventory operation supplies it. Queries spanning accounts run a bounded list of independent, explicitly keyed requests, never an unscoped query. A single partition is appropriate for the stated hundreds of numbers; estimate actual document size, RU and contention before rollout. Cosmos limits still apply. A future partition redesign is a separate approval.

Alternatives: storing inventory in SQL adds a second store to the carrier runtime and needs new tables/migrations; querying existing voicelines is forbidden because each DID has its own partition. Alert records do not preserve claims, purchases or retry state. Neither alternative solves this as economically as a small operational inventory.

**Generation invariant:** the monotonically increasing assignment generation belongs to the asset across businesses, not to a per-business counter. Slot/profile projections copy it. Any routing mutation validates the current asset/slot and operation immediately before the line write; same-generation forwarding operations also compare the operation ID and expected old target. Removing/reassigning a line advances the generation. A worker losing its claim must not retry a stale projection. Runtime ingress must check assignment readiness/fencing through a bounded, fail-closed authorization path; an eventual projection alone cannot provide strict isolation. Reuse the existing live-call binding where possible after a full host review; do not add a Cosmos read to every media frame.

Daily spend must specify its accounting basis in settings: recommended maximum new rental+setup exposure committed today, separated by currency and including reserved unknown purchases. Forecast next-cycle renewals separately; this counter is not a carrier invoice. A pool assignment must still pass the rental cap and renewal-horizon rules even though it consumes no new purchase count.
