## 3. Very tall (and very wide) pages — DECIDED: build it right, with no degradation

**Problem:** vision renders each page to fit a 1024 × 1024 box (`Voice:Knowledge:Vision:PageRenderMaxEdgePixels`),
the verifier to 2048. A 1080 × 11,966-pt page becomes ~92 px wide (~185 px at 2048) — unreadable. Also inspect the
banked Document Intelligence result for this document: its documented PDF page-size limit is 17 × 17 in, so it may
have read little or nothing.

**Design (industry-standard tiling):**
- A page whose aspect ratio exceeds a threshold (setting; recommend > 2:1, measured on real brochures) is read in
  ‼️ **SUPERSEDED (session 2):** the trigger is reading scale (< 0.6 × A4) OR an edge over Document Intelligence's 17 in — `DESIGN-TALL-PAGES.md` §2 (approved).
  **sections**: fit the page's WIDTH (or height, for a very wide page) to the readable scale, and cut it into
  overlapping sections along the long side.
- **Cut where nothing is split:** when Document Intelligence read the page, place each cut in a horizontal gap between
  lines, never through a line, table, figure or heading (use its line/table/figure coordinates). Only when no gap
  exists within a section's reach, cut with an overlap band and de-duplicate the overlap when stitching.
  ‼️ **SUPERSEDED (session 2):** NO overlap cut — text is never cut; a section may grow to 1.5× or cut a picture with no text on it (`DESIGN-TALL-PAGES.md` §4.5). The cut evidence is the page's own text layer + picture boxes + an ink profile (the whole-page Document Intelligence read is noise on these pages).
- **Stitch in reading order** into one page transcript, so chunking, headings, picture anchors and citations see ONE
  page exactly as they do today. Page numbers stay the document's page numbers (a section is never a "page" to the
  provider, the cards or the citations).
- **Render one section at a time** (a clipped region) — never the whole strip at full scale (the strip at 2048 px wide
  ‼️ **SUPERSEDED (session 2):** sections of a page are read IN PARALLEL (a table continuation re-read once with its header); the library is `bblanchon.PDFium` 156.x (approved) — `DESIGN-TALL-PAGES.md` §5, §9.
  would be ~186 MB for one bitmap). PDFium can render a clipped region; Docnet.Core 2.6 does not expose it — evaluate
  the right API/library (licence, Linux support, thread safety) and ASK before adding a package.
- Verification (the "source check") runs per section with the same rules.
- Settings for threshold, section size, overlap, maximum sections per page; the page cap and cost accounting count
  sections as vision work.
- **Edge cases (owner: "it's not gonna just simply cut it randomly" — every one of these has a designed answer and a
  test; the list is examples only):**
  - **Nothing meaningful is ever split.** A cut lands only in a real gap between lines. Never through: a line of text;
    a word — including a word broken across two lines with a hyphen, a word containing an apostrophe (`provider's`,
    `don't`), or a number, price or date (`$1,299.00`, `12/10/2026`); a table row or a whole table; a picture; a
    heading and the paragraph it introduces; a list item; a caption and its picture; a footnote marker and its note.
  - **Paragraph continuity:** a paragraph that runs across a cut is stitched back as ONE paragraph (the overlap
    de-duplicated, sentence order preserved), so chunking and meaning are exactly what an uncut page would give.
  - **Tables:** a table taller than one section is kept whole in one section when it fits the section cap; when it
    cannot, it is split only between rows, the header row carried so each part stays readable, and rows re-joined into
    one table when stitched — never a row in two halves, never a duplicated row.
  - Multi-column layouts (reading order inside and across sections); text laid over a picture; watermarks and
    background text; repeated headers/footers; superscripts, subscripts and footnotes; right-to-left and non-Latin
    scripts (Hindi, Gujarati and every language the product supports — cuts must respect their line boxes too).
  - A picture spanning a cut (belongs to the section holding most of it, pinned once); rotated pages; very WIDE pages
    (panoramas, wide tables — section horizontally); a tall page inside a normal document (only that page is
    sectioned); extremely long strips (section cap + a plain notice); a scanned tall page with no text layer (no line
    coordinates — cut with overlap and de-duplicate); a page Document Intelligence refused or read partially; a section
    that fails transiently (retry that section only); a crash mid-page (sections are banked like pages, never repaid).
- **Tests:** unit tests for the cut placement on synthetic layouts built for each case above; integration tests on real
  engines; and REAL uploads through the product on a sandbox business (this brochure, a long infographic, a tall menu,
  a tall price table, a document in Hindi and one in Gujarati), each checked in Ask Clinket and the receptionist path.
- **No-degradation proof:** pages under the threshold take today's exact path — prove it with byte-identical cards
  for a sample of existing sandbox documents before/after. Then prove this document reads correctly in Ask Clinket and
  the receptionist. State the extra vision cost (sections per tall page).

## 5. Search presentation — O1, O2, O3 all DECIDED (owner 2026-09-29)

### O1 — consistent scores on typed searches
- Plain words: Azure keeps each index in several pieces and, when scoring a typed word, measures how rare that word is
  inside ONE piece, not the whole index. The same service can score differently depending on which piece holds it; with
  one row per area, one service's rows sit in different pieces and typed results shuffle slightly for no reason.
- Fix: `SearchOptions.ScoringStatistics = ScoringStatistics.Global` on typed (text) queries (SDK 12.0.0 supports it;
  documented cost: some added latency). Golden rule: before/after on sandbox clones — order stability and latency.

### O2 — "Serves Hamilton · Based in Toronto" for providers who travel to the customer
- Today a Toronto-based provider serving Hamilton shows "42.7 km" to a Hamilton customer and sorts far on "Distance".
- Build:
  - **Services the customer goes to** (at the business): distance to the business address — unchanged.
  - **Services that come to the customer:** inside a served area the card says **"Serves Hamilton"** with a second
    line **"Based in Toronto"**; outside every served area it shows the distance to the nearest served area, plus
    "Based in Toronto". The Distance sort uses the same number (0 inside a served area). A local Hamilton provider shows
    "Serves Hamilton" too, so neither is favoured — rating and relevance decide.
  - Plain words (§0.20), all five languages, web + both mobile apps; the provider list and the service list alike.
- First check which fields each per-area row carries (area centre, radius, area name). If a new index field is needed,
  ‼️ **RESOLVED (session 2):** no new index field is needed — every row carries all its areas; containment is checked at the index with the verified `serviceAreas/any(...)` filter. `FINAL-PLAN.md` W8.
  present the §0.7 table and wait.
- Proof: before/after lists for a travelling provider and a local one in the same city.

### O3 — "Most reviewed" ordered correctly across every match
- Today the card shows the service's own review count, else its business's; no single index field holds that number,
  so "Most reviewed" on a browse re-orders only the first relevance window (`Search:MaxResultDepth`). ("Top rated" is
  already right: confidence-adjusted and ordered at the index, D-97.)
- Build: ONE sortable index field holding exactly the number the card shows, written by the one document builder; order
  "Most reviewed" at the index; the card reads the same value so the two can never disagree.
- **Owner asked:** the name must be correct and make sense, and the field should be **nullable** so a listing with no
  reviews stores nothing. Recommendation: **`listingReviewCount`** (`Edm.Int32`, sortable only — not searchable,
  filterable or facetable; **null when there are no reviews**). Null sorts last on "most reviewed" (descending) and first
  on the rare ascending order — the same place as zero, so behaviour is correct. Confirm the name against the existing
  `…ReviewCount` fields before building; present the full §0.7 table (the owner approved the field itself — the table
  records name, type, reader, writer, cost).
