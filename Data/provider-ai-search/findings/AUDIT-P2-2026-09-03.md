## 2. ‼️ THE THREE FINDINGS THAT MATTERED MOST

### 2.1 ZERO web tests existed for the whole feature (dimension 9)

The P2 web change added 18 files. Exactly one was a test — `useDictation.test.js` — and that is P1.5's mic
suite, not P2's. Every *registry* was covered; nothing that computes an answer was.

The consequence was not hypothetical. `askRules` and `redactQuestion` ship as **twins**, one per platform,
and the only tests over them lived in the *mobile* repo as a parity suite — which reads the peer tree and
therefore **skips in CI** (§0.17). So in web CI those two files were tested by nothing at all, and a
genuine web-only redaction defect shipped and survived (§4.2 below).

**Fixed.** 106 web tests across four suites, all green:

| Suite | Tests | What it holds |
|---|---|---|
| `src/lib/businessSearch/askRules.test.js` | 40 | frame parsing, the page rule, the chip rule, source counts |
| `src/lib/businessSearch/redactQuestion.test.js` | 36 | every shape that used to survive, measured against the old rules |
| `src/services/businessSearchService.test.js` | 16 | streaming, keep-alives, split frames, 400/403/429, the 401 refresh, cancel, stall |
| `src/utils/recentQuestions.test.js` | 14 | per-business isolation, the cap, the sign-out sweep, and that the sweep is CALLED |

### 2.2 ‼️ A guard that asserted a function's name in the file that DEFINES it

`clearAllRecentQuestions` — the sign-out sweep for the member's stored questions — existed on both
platforms and **was called from nowhere**. I wired it up. The guard I wrote for it read
`src/utils/recentQuestions.ts` and asserted the string `'clearAllRecentQuestions'` appeared there.

That is the file the function is *declared* in. The assertion was true before the fix, true after it, and
would stay true if both call sites were deleted tomorrow. **It could not fail.**

This is §0.17's own lesson — *"green must mean 'I checked', never 'I couldn't look'"* — in a new costume:
not a scan that read zero files, but a scan pointed at the wrong one.

**Fixed** on both platforms, at the call site:
- mobile — `expect(read('src/services/tokenManager.ts')).toContain('clearAllRecentQuestions()')`
- web — a real behavioural suite (write two businesses' questions, purge, assert both gone, assert a
  foreign key survives) *plus* a call-site assertion against `clientStatePurge.js`.

### 2.3 ‼️ The dictation strip rendered INSIDE the rounded ask pill — on both platforms

Severity 1, and the same structural mistake twice.

`DictationMic` (web) and `SpeechToTextButton` (mobile) each render a **vertical stack**: the round mic
button, then the state message, then Try again, then the language-correction chips. Both were mounted as a
single child *inside* the ask input's horizontal row — `flex items-center … rounded-full` on web,
`flexDirection: 'row', borderRadius: 999` on mobile.

So "Listening…", "Microphone blocked", "Try again" and the language chips all rendered **inside the pill**,
in a narrow column between the text field and the send button. On a phone the message wrapped to a few
characters per line; on web it broke the pill's shape.

**Fixed by splitting the control from its status on both platforms**, so each half is placed by the caller:

- **web** — `DictationMic` (button + clock, inside the pill) and a new `DictationStatus` (message + chips,
  below it, full width). The strip JSX moved verbatim; the default export is unchanged.
- **mobile** — `SpeechToTextProvider` owns the hook **once**; `SpeechToTextMic` and `SpeechToTextStatus`
  read it through context. Nothing is recorded twice, no state is duplicated, and the strip, Try again and
  the chips are the same code in a new place — the owner's P1.5 instruction *"DO NOT rebuild them"* held.
  `SpeechToTextButton` remains as the composed control.

## 3. CORRECTNESS & CONTRACTS

### 3.1 ‼️ The 401 refresh retried an answer the member had already stopped

Found by a test written before the code was trusted, and **RED on the first run**:

```
● the 401 refresh › does NOT retry after the member pressed Stop mid-refresh
  Expected number of calls: 1
  Received number of calls: 2
```

`askBusinessSearch` checks `!signal?.aborted` *before* the refresh, then awaits it — a network round-trip
of its own — and retries without re-checking. Press Stop during that window and the retry went out anyway.

Worse, it went out **uncancellable**: `askOnce` wires the caller's signal with
`signal.addEventListener('abort', …)`, and an **already-aborted signal never fires its `abort` event**, so
the listener could never run. The member is charged one of their daily questions for an answer they
stopped, and it streams onto a screen they have left.

**Fixed in two places, both platforms:**
- `askOnce` returns a cancelled result immediately when the signal is already aborted, before anything is
  constructed. This is the general guard — it covers every caller, not just the retry.
- the retry gate re-checks: `if (refresh?.success && !signal?.aborted)`.

Mobile's `sseStream` already had the pre-construct check, so no request escaped there; the gate now reads
identically on both twins.

### 3.2 The other eight, all fixed

| # | Defect | Fix |
|---|---|---|
| 1 | No request identity — a superseded stream wrote into the new question's state | `runIdRef`/`reopenIdRef` + `isLive()` on every setter |
| 2 | A stream that ended with no terminal frame was not marked cut-short | `sawTerminal` → `setPartial(true)` |
| 3 | The same picture could arrive twice and render twice | dedupe on url |
| 4 | `replayed` was *inferred* from other state | explicit state |
| 5 | Analytics and `rememberQuestion` fired **after** the liveness gate, so a question the member really asked went unrecorded when superseded | moved **before** it |
| 6 | A 400 showed a generic failure, discarding the server's actionable message | renders the server's message |
| 7 | `reopen` had no `try/catch` and dropped `asked` on failure | guarded, keeps `asked` |
| 8 | `citationActionKey`, `streamFailureKey` — exported, called by nobody | deleted |

`answeredFromKey` was added so the "answered from …" line resolves **one key per shape** rather than a
sentence assembled from fragments — the latter cannot be translated correctly into any of the five
languages.

## 5. TENANT ISOLATION & AUTHORIZATION

### 5.1 ‼️ Two effects read `access`/`accessError` and did not depend on them

ESLint reported it as `react-hooks/exhaustive-deps`. It is not a lint nit — it is a permission defect.

`access` loads **asynchronously**. On the mobile screen, the knowledge-nudge effect and the
service-names effect both gate on
`capabilityReadState('…', can, access !== null, Boolean(accessError))` but listed only
`[activeBusinessId, can]`. A member whose grants resolved *after* mount would never re-run either effect —
so the document nudge never appeared and, worse, **`serviceNames` stayed null, which means no chips at
all**. The owner's explicit requirement that the chips be built from the provider's own catalogue would
have silently failed for exactly the members whose access read was slow.

Fixed: `[activeBusinessId, can, access, accessError]`, matching the third effect on the same screen, which
had it right.

### 5.2 The other two

- Every capability read on both platforms goes through `capabilityReadState`, whose four outcomes keep a
  **failed** access read distinct from a **denial**. A bare `can()` collapses them, and the collapse
  direction is the dangerous one.
- Mobile's hand-rolled stream bypasses the axios interceptor, so a 403 raised no shared refusal dialog.
  `raiseAccessDenied(describeRefusal(error))` is now called explicitly, and the web client sets
  `error.config` where `describeRefusal` actually looks — on the **error**, not inside `response`.

### 5.3 What the request carries

Pinned by test: the ask body contains **only** `question`, `sessionId` and `language`. No `businessId` — the
server takes tenancy from the token, and a client-supplied business id is the shape of a cross-tenant bug.

### 6.2 ‼️ The busiest tap on the surface was compared on NEITHER side

Both platforms emitted `` resultType: `source_${action}` ``. The parity resolver collapses a template hole
to `*`, and `comparable()` rejects any key containing one — so the most-used `ResultClick` on the whole
feature was invisible to the guard on both platforms simultaneously.

**Fixed** by writing all four names out in full — `source_service`, `source_offer`, `source_profile`,
`source_hours` — inside four branches that were already there for routing. Verbose by four lines, and now
both greppable and comparable. The guard passes having actually compared them.

The shared twins (`askRules`, `redactQuestion`) are dependency-free and side-effect-free by design, so the
parity suite compares behaviour rather than shape. Mobile's pictures, the three source tints, the pinned
step strip and the collapsed source list were all brought to the web rendering rules in this phase.

### 14.3 ‼️ The mobile dashboard greeting was dead — it had been built and never rendered

ESLint's one error in the mobile repo was `'personName' is assigned a value but never used`. Behind it:

- the name **was** being fetched from `userInformation` and set into state (`index.tsx:163-174`),
- a comment stated the intent — *"The greeting names the PERSON, exactly as provider web does"*,
- `MY_DASHBOARD.WELCOME_BACK` and `MY_DASHBOARD.WELCOME_PREFIX` **shipped in all five languages**,

So the work was done and wired to nothing: **every provider saw "My Dashboard"** where web says "Welcome
back, Sam". Fixed to mirror web's `Header.jsx:136-143` exactly, and the now-orphaned `MY_DASHBOARD.HEADER`
removed from all five catalogs (§22.11).

### 14.4 ‼️ AND A NEAR-MISS OF MY OWN, IN THAT LAST FIX — recorded because the class is the dangerous one

Removing the orphaned key, I ran `/^[ \t]*"HEADER": "[^"]*",[ \t]*\r?\n/m` over each catalog. `/m` anchors
per line, not per object, so it matched the **FIRST** `HEADER` in each file — **`ADD_BULKUPLOAD_SERVICES.HEADER`
("Bulk Upload Services") in all five languages**, not `MY_DASHBOARD`'s. My own verification print said
"MY_DASHBOARD still has 118 keys, WELCOME_BACK=true" and was **true and useless**: it confirmed what I had
not touched.

`git diff` caught it. The repair could **not** be `git checkout --` (§0.19 — other sessions hold
uncommitted work in those files), so instead: read each language's value from `git show HEAD:`, re-insert
the line at its original position, then redo the intended removal **scoped to the `MY_DASHBOARD` object**,
and finally assert key-by-key against HEAD that **nothing except `MY_DASHBOARD.HEADER` was lost**. All five
verified.

**The lesson, stated plainly:** a regex is not scoped to the object you are thinking about, and a check that
asserts what you did not change proves nothing. Diff before believing yourself.

## 14.5 ‼️ A LATE ORPHAN-KEY SWEEP FOUND A DEFECT NO TEST COULD SEE — AND THE AUDIT ITSELF LIED ONCE

Asked whether anything was still pending, I ran the localization sweep in the **orphan direction** — keys
that exist in a catalogue and are read by nothing. That direction is the one that finds *missing UI*, and it
found three things and one false claim of my own.

### 14.5.1 ‼️ The "answered from" line rendered a RAW KEY to the provider

`answeredFromKey` lives in the shared rules and answers with a **web** key
(`BusinessSearch.Answer.AnsweredFromDocuments`). Mobile's catalogues are nested UPPER_SNAKE, so the screen
maps web ids through small translators — `chipKeyToMobile`, `errorKeyToMobile`. **There was no mapper for
the answered-from family**, and the screen did `t(answeredFrom.key, …)`.

i18next, given an id it does not hold, **returns the id**. So the line under every answer on the phone read
`BusinessSearch.Answer.AnsweredFromDocuments` to the provider. Eleven keys shipped in all five languages
and were read by nothing.

- **Why no test caught it:** every suite asserted the *screen* rendered a value and that the *catalogue* held
  the keys. Nothing asserted the two vocabularies met.
- **Fixed:** `answeredFromKeyToMobile`, in the same idiom as its two siblings.
- **Guarded, and the guard was SABOTAGE-VERIFIED:** a new block in
  `businessSearchScreenRegistration.test.ts` derives every `BusinessSearch.*` key the shared rules can
  return (12 today), asserts each is mentioned **only inside a mapper**, and asserts no `t()` argument is a
  rule-supplied value. Removing the mapper from the call site turns it RED (1 failed of 37); restoring it
  from a **scratchpad snapshot** — never `git checkout` (§0.19) — turns it green.
- ‼️ **The class, for P3:** every shared rule that returns a key needs a mapper on mobile, and P3 adds more.

### 14.5.2 A hardcoded English string a screen reader would read aloud

`AskAnswerMarkdown.tsx` labelled each citation pill `` `Source ${number}` `` — hardcoded English (§0.10),
while `BUSINESS_SEARCH.ANSWER.SOURCE_LABEL` shipped in all five languages and was read by nothing. Web
