## 2. THE FIVE FINDINGS THAT MATTERED MOST

### 2.1 ‼️ "Open booking" opened nothing — on BOTH apps (dimension 6)

The citation carried `booking.BookingId`. Both apps open a booking at `/bookings/{bookingNumber}`, and the
API route is `[HttpGet("{bookingNumber}")]` resolving `GetBookingByNumber`. The card's one action therefore
led to an empty screen, which reads to a provider exactly like the booking having been deleted.

The same class hit **invoices** (both apps route by `invoiceNumber ?? invoiceId`, as their own lists do).

**Fixed** — `ListBookingsTool` cites the number; `ListInvoicesTool` cites `reference`.
`BusinessSearchMoneyToolTests.ListInvoices_CitesTheNumberTheAppsRouteBy` pins it.

Alongside it, five more destinations were wrong or dead:

| Action | Was | Now |
|---|---|---|
| booking / quote / invoice / lead (web) | list + `?highlight=` — a query **no page reads** | the app's own `[id]` detail route |
| customer (web) | list + `?highlight=` | the list, with no invented query |
| call (web) | `?callId=` — no reader exists | the Call follow-ups page |
| review (web) | the reviews page, ignoring `recordId` | `?reviewId=`, the param `Reviews.jsx` already scrolls to |
| quote (mobile) | `{ quoteId }` — the screen reads `quoteInfo` | `{ quoteInfo: { quoteId } }` |
| invoice (mobile) | `{ invoiceId }` — the screen reads `invoiceNumber` | `{ invoiceNumber }` |
| lead (mobile) | `{ broadcastId }` — the screen reads `broadcastInfo` | `{ broadcastInfo: { broadcastId } }` |
| conversation (mobile) | the inbox LIST | the thread, as web does |

**Guard added:** `clinqetmobilepartnerapp/__tests__/businessSearchNavigation.test.ts` reads the screen's own
`navigate()` calls and checks each param against the destination screen's source. **Sabotage-proven:**
reverting the quote param to `{ quoteId }` turned 2 of its 8 tests red; the file was then restored from a
scratchpad snapshot copy, never through git (§0.19).

### 2.2 ‼️ The line under the answer COUNTED a capped sample (dimension 3)

`BusinessSearch.Answer.AnsweredFromWork` read *"From {count} of your records"*. The cards are a **sample**
bounded by `WorkLists.MaxRows`, so a business with 47 bookings got *"From 10 of your records"* — a number
the provider reads as the total, sitting directly under a sentence stating the real one.

Approved sheet **M5 §14** rules on this explicitly: the quiet line is *"Answered from bookings · your own
work"* — **"never a count."**

**Fixed** on both twins: `answeredFromKey` now returns a count-free key naming the KIND
(`AnsweredFromBookings` … `AnsweredFromRefunds`), or the neutral `AnsweredFromOwnWork` when two kinds of work
were cited. The counted key was **deleted** from all ten client catalogues (§22.11).
`askKeys.test.js` asserts, per language, that no work line contains `{` or `#`.

The same finding removed the word *"records"* from provider-facing copy — the sheet uses it only in its own
narration, never in a frame.

### 2.3 ‼️ Five tools put a raw English enum name on a card, in every language (dimension 5)

`ListQuotesTool`, `ListInvoicesTool`, `ListLeadsTool`, `ListTeamMembersTool` and `SearchRefundRequestsTool`
each set `Subtitle = x.Status.ToString()`. A Gujarati-speaking provider's invoice card read
`PartiallyPaid`; a refund card read `CounterpartyDeclined`. That is a §0.10 violation on the shipped screen.

**Fixed** with one `StatusWord(key, language)` helper on the work-tool base that returns **null** when the
catalogue has no entry — because a card with no status is honest and a card showing a raw key is not.

- Booking, quote and invoice reuse the platform's existing `PDF_*Status.*` words, so a card and the invoice
  PDF can never disagree.
- Lead, member and refund had no family: **21 new keys × 5 languages = 105 entries** minted.
- `ListReviewsTool` also had `"{rating}★"` — a glyph. Now `{0} stars` / `{0} star`, per the sheet's own copy.

### 2.4 ‼️ Eleven card labels the approved sheet draws were not rendered (dimension 7)

M5 §06 draws `<span class="lbl work">Booking</span>` above the title of **every** work card, and §14 lists
"card labels and buttons" as the screen's own. Neither app rendered one, so a customer card and a teammate
card were both just a person's name with no word for what they are.

**Fixed:** `kindLabelKey` in the shared rules + a chip on both `SourceCard`s, reusing the existing three
tints (work green · call blue · money amber) so the colours cannot drift. 11 keys × 10 catalogues.
Non-work cards keep no label, as M2 approved them.

The **call note** was also being drawn twice — once as the server's `Subtitle`, once as the screen's own
line. §14 assigns that sentence to the *screen*, which is also correct on the merits (the answer's language
and the UI's language are not the same thing). The server now sends the call's **intent** as the subtitle,
which is what the sheet's second line shows.

### 2.5 ‼️ A chip was offered to members who would then be refused (dimension 2)

`capabilityReadState` deliberately answers `"allowed"` when the access read **failed**, so a transient
failure never locks a member out of their own screen. The chip gate used it — so on a failed read, "how many
bookings this week?" was offered to a member who may hold no `booking.read` at all. Tapping it spends one of
their day's questions on a refusal, which is exactly what the file's own "A CHIP IS A PROMISE" rule forbids.
The comment above the code even *claimed* the property the helper does not provide.

**Fixed** on both apps: `capabilityAccessState(...) === "granted"` — false while loading, false on failure,
true only when the permission is actually held.

## 6. COST & PERFORMANCE — REVIEWED, NO DEFECT FOUND

- Every Cosmos query is **partition-scoped**: `businessId` is the partition key and is passed on both the
  items and the count leg (§0.6). Proven, not asserted — see finding 16.
- The two legs are issued **together** (`Task.WhenAll`), never sequentially.
- `invoice_totals` issues its paid-rows read and the page's summary concurrently.
- The roster is **lazy**: a knowledge question issues no roster read at all — the property P1.5 bought by
  removing the eager `IsSolo`, and one this phase does not spend again. Cached per business, `Size = 1`.
- The business time zone is cached (`bsearch:tz:`), and a **failed** profile read is deliberately not cached.
- `CapPayload` bounds what one tool result may put in the prompt; rows drop from the tail rather than being
  truncated, because a cut string hands the model a broken document.
- The roster in the system prompt is capped by `Members.MaxNamesInPrompt` and is added **only** when the
  member could narrow by person at all.

## 7. SCHEMA — §0.7 DID NOT FIRE

No approval was requested because none was needed, and that was established with evidence before any code:

- **Cosmos:** no new container, no partition-key change, **no new field on any entity**. The two new range

- **SQL:** no table, no column, no index. `ListForBusinessInRangeAsync` uses the existing `(BusinessId,

- **Search:** untouched.
- The only new persisted-shape change is on a **wire DTO** (`BusinessSearchCitationDto.RecordId`), and
  citations are not persisted — `PersistTurnAsync` stores the question and the answer text only.

## 8. ACCEPTED RESIDUALS — named, not hidden

1. ~~**The model-facing wording was NOT re-measured.**~~ ‼️ **CLOSED 2026-09-03, on the owner's instruction —
   `findings/MEASUREMENTS-P3-2026-09-03.md`, 1,175 live calls against `gpt-5.6-luna` @ `reasoning_effort:
   none`.** `relativeRange` **175/175**; the follow-up carry-forward (the owner's own case) **125/125**; and
   money **FAILED at 183/200** — the `kinds` note's *"never total **them** together"* was read as licence to
   total within one direction, producing `4500 + 12000 = 16,500`. Cause diagnosed over four variants,
   both halves fixed, re-measured at **196/200**. ‼️ **A residual remains and is a PRODUCT decision, not a
   prompt one** — see §8.7.
2. **Sheet M5's `rec-line` on the refund card** (the customer's reason) is not rendered — see §5. The reason
   reaches the model and appears in the answer's prose.
3. **Sheet M5's exact subtitle phrasing** for the customer, message, review and Insights cards ("4 bookings ·
   last on 2 Sep", "Unanswered since Mon 1 Sep", "29 Aug · no reply yet", "Bookings, earnings and reply
   time") is not reproduced; those cards show a neutral, already-localized fact instead. No card shows
   untranslated text. **Carried to P4** as a copy pass.
4. **`get_voice_usage` was deliberately not built.** Allowance data belongs to the ai-billing family the
   owner excluded on 2026-09-02.

5. ‼️ **T7 — a saved conversation replays the stored ANSWER TEXT verbatim, and it is not re-authorized.**
   `AUTHORIZATION-DESIGN` §2's threat table says of T7: *"Only opaque handles are replayed; each turn
   re-authorizes."* The citations are indeed handles — but the **answer's prose is not**, and
   `GetSession` returns `t.Content` unchanged. So a member whose scope is narrowed after asking (role
   downgrade, removal from a team, suspension) can reopen the conversation and read figures they could no
   longer obtain today.

   **Scope of the exposure is narrow:** the session is member-scoped (`GetMemberSessionAsync(sessionId,
   businessId, membershipId)`), so it is only ever *their own* past question and the answer *they were
   legitimately given at the time*. It is history, not a new disclosure — but it is not what the design
   document claims, and the gap should be closed or the claim corrected.

   ‼️ **NOT BUILT, because closing it needs a stored field — §0.7, and that is BLOCKING.** The turn would
   have to carry the `AuthorizationVersion` it was produced under so replay can compare. **The owner's answer
   is required before any code.** The §0.7 table:

   | Column | Answer |
   |---|---|
   | **What** | `AiSession.History[].AuthorizationVersion` — an `int` on the existing turn object in Cosmos |
   | **Who reads it** | `BusinessSearchController.GetSession`, comparing against the caller's live `TenantContext.AuthorizationVersion` |
   | **Who writes it** | `PersistTurnAsync`, from the same context that answered |
   | **Why not a column** | Cosmos, not SQL; it is one-to-one with a turn, so it is a field on the turn, never a document of its own |
   | **Why not a constant/enum** | It is a per-turn value that changes with every grant change |
   | **Why not already stored** | Checked: the turn stores `Role`, `Content`, `Timestamp` only. `AiSession` itself carries no version |
   | **Cost** | One `int` per turn. No new index — it is read only after a point-read of the session the member already fetched |
   | **What breaks if omitted** | Nothing today, for the reason above: it is the member's own history. The honest answer is that this is a **design-claim correction**, not a live leak — which is exactly why it is the owner's call whether to spend a field on it, or to amend T7's wording instead |

7. ‼️ **THE MONEY RESIDUAL — FOUND, THEN CLOSED AT 500/500.** After the first fix, ~4 of 50 direct
   "what do they come to in total?" questions still invented a figure, and I escalated it to the owner as a
   product decision claiming prompting could not close it. **That was wrong.** The cause was an ABSENCE that
   was never stated: the payload carried no combined figure and never said so, so the model was asked for
   something the result neither carried nor denied. One sentence naming the absence
   (`BusinessSearchToolNotes.NoRefundTotalExists`) took it to **500/500** on the shipped code across five
   questions, two of which press hard for a single figure. **No product decision is required.**
   Full working: `findings/MEASUREMENTS-P3-2026-09-03.md` §3d–§3e.

   ‼️ **The reusable rule:** when the model reaches for something the payload does not carry, **state the
   absence** — do not forbid the act harder. And state it about the RECORDS, never about the model's
   ability. A variant that instead renamed the count field off the word "total" made it **worse** (42/50),
   so the hunch was measured before it could ship.

8. **A prompt-cache hazard, identified and NOT fixed.** The multi-script SEARCH WORDS block is appended to
   the **system** message only when the question needs more than one alphabet, so for a multi-alphabet
   business the prompt prefix changes between questions and that turn misses the cache. Moving it into the
   user turn would fix it — **but its wording measured 25/25 where it sits (P1.5 Gate 1), so it must be
   re-measured, never merely moved.** Carried to P4 as C1(b).

6. **The refund amount's SHAPE differs from the Refund requests page.** The tool emits
   `INR 12345.67` (currency code, invariant, ungrouped); the page renders
   `intl.formatNumber(..., {style: "currency"})` → `₹12,345.67`. The **number and the currency are both
   correct** — and the JPY/KRW exponent bug is fixed — but the payload orders the model to quote the string
   "character for character", so the difference reaches a provider cross-checking against their screen, and
   the missing thousands separator makes a five-figure refund harder to read.

   **Not fixed inside P3, deliberately.** Matching the browser's ICU output byte-for-byte from .NET is not
   achievable, and the two remaining options are both worse than the residual: changing
   `CurrencyMinorUnit.ToMajorString` alters money formatting in **every** consumer platform-wide, and adding
   a second formatter here is exactly how a card, a PDF and a page start to disagree. **Carried to P4** as a
   platform-level money-formatting question.

## 9. THE OWNER'S OWN CASE

> *"admin ask how many booking and then say its team name have then it should be able to handle it"*

Built and pinned by `BusinessSearchFollowUpTests` (6). The chain is: the roster goes into the system prompt
**once**, gated on the member being able to narrow by person at all; the model returns a membership **id**,
never a name; the server validates that id against the same roster; an id that is not on it produces an
explicit `MemberNotFound` refusal (**not** "nothing is assigned to you", which is a different and wrong
answer); and the answer names the member it actually used, so a wrong person is visible in one glance.
