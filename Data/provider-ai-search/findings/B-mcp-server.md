## 1. Executive summary

1. **The premise "the MCP is reachable only by the Function app" is false in code.** The Main API is already an MCP *client* of `Clinqet.Mcp`: `clinqetapi/Clinqet.API/Services/McpToolGateway.cs` mints a **Partner-scope per-session call token** with call-id prefix `chat-`, upserts a `VoiceCallSession` binding doc, and speaks Streamable-HTTP MCP to `{Mcp:PublicUrl}/mcp/{Mcp:SecretPath}` (`McpToolGateway.cs:55-66,71-85`). The in-app text assistant (`McpAIService`) drives every tool call through it (`clinqetinfrastructure/Services/AI/McpAIService.cs:155-168,601-615`). `McpToolDiscoveryService.cs` / `McpToolExecutionService.cs` do **NOT exist** anywhere (grep of all repos).
2. **Auth is a 3-tier channel model with no ASP.NET auth scheme at all**: secret URL segment (fixed-time) + per-call HMAC JWT (`businessId`,`callId`,`scope`,`jti`) + a Cosmos binding doc (`vcall_{callId}` in **SystemData**, pk `/pk`) whose `Jti`/`BusinessId`/`Scope` must match the token (`clinqetmcp/Clinqet.Mcp/Middleware/McpChannelAuthMiddleware.cs:92-176`). Server-to-server routes (`active-calls`, `provider-join`, `warm-context`) use `X-Internal-Api-Key` instead (`:29-31,99-111`). A provider JWT is never accepted by the MCP.
3. **Tenant scope is structural**: no tool takes a `businessId`; every tool reads `CallContext.BusinessId` inside `McpToolGuard.ExecuteAsync` (`Tools/McpToolGuard.cs:47-51,87`) and every repository/search call is partition- or filter-scoped to it, with per-row post-verification for AI Search (`clinqetinfrastructure/Services/Knowledge/ProviderKnowledgeSearchService.cs:131-132,501-509,672-706`).
4. **Authorization is binary** — `VoiceCallScope.Customer|Partner` (`clinqetshared/Enums/VoiceCallScope.cs:6-10`). The MCP host has **no SQL**, knows nothing of `BusinessMembership` / `RequiresPermission` / `TenantContext` (grep: only a comment at `Program.cs:225-226`). A `chat-` session is Partner-scope for the whole business regardless of the member's permissions; the API gate is a single key `ai.assistant.use` (`clinqetapi/Clinqet.API/Controllers/AI/AIAssistantController.cs:431,445`).
5. **33 tools in 10 classes** (`Program.cs:420-431`), 16 of them on the chat allowlist (`clinqetshared/Models/McpServerSettings.cs:49-55`); `search_knowledge`, `answer_catalog_question` and every send/verify/OTP/voice tool are chat-refused server-side (`McpToolGuard.cs:67-74`) and filtered client-side (`McpToolGateway.cs:113-116`).
6. **The caller-facing phone assistant cannot answer business-internal questions** because a Customer-scope token is refused every `partnerOnly:true` tool (`McpToolGuard.cs:76-82`), `get_provider_context` returns only the public subset in Customer scope (`Tools/ProviderContextTools.cs:27-34`), the realtime session's `allowed_tools` is the 16-name Scope-C list plus gated extras (`clinqetinfrastructure/Services/Voice/RealtimeSessionPayloadBuilder.cs:21-71`), and the prompt forbids inventing/revealing (`:400-402`). Adding a provider-JWT path elsewhere does not change any of these.
7. Results are JSON (Web camelCase, non-ASCII unescaped, enums as strings — `Program.cs:413-418`); model-facing guidance text is **hardcoded English**, not localized (e.g. `Tools/BookingTools.cs:1362-1380`). Size caps: `TransactionsMaxPageSize=25`, catalog `LookupMaxResults=5`, knowledge `RetrievalTopK=8`/`RetrievalMaxTokens=3000` (`Clinqet.Mcp/appsettings.json:78-80,100-101,182`).
8. Rate limiting is an **in-process** per-business window (60/min) + concurrency cap (4) (`RateLimiting/McpToolRateLimiter.cs:44-98`); audit = one metadata-only `McpAudit` row per tool call in **ProviderData** partition `businessId` (`clinqetinfrastructure/Data/COSMOS/McpAuditRepository.cs:19,28-29`).
9. Deployed per voice stamp (`ca` **and** `in`) as `clinket-mcp-{stamp}[-env]` on a dedicated P0v3 plan, default-deny IPs + API/Functions outbound IPs (`azureautomation/deploy.ps1:1477,380-386,3807-3825`); the API already has `Mcp:PublicUrl` wired per stamp (`deploy.ps1:7198-7206`; `clinqetapi/Clinqet.API/appsettings.json:2037-2041`).
10. For Provider AI Search the reusable pieces are the **infrastructure services the tools wrap** (`IProviderKnowledgeSearch`, `IProviderCatalogSearch`, `IFullProviderContextService`, the repositories) — all in `clinqetinfrastructure`, hostable in the API — and, if the MCP is to be reused, the existing `McpToolGateway` seam. A member-permission-aware path cannot be enforced inside the MCP today without adding a new concept (claims/binding fields → §0.7 approval).
11. SKILL.md `clinqet-voice-assistant` disagrees with code in ~9 places (package version, tool count 30/29 vs 33, class count 9 vs 10, S2S route list, `SessionStartSignalAttempts` 3 vs 2, binding-doc container, CallContext fields, "chat MCP is in-process"). Listed in §2.10.

### 2.4 Tool result shaping

- **Serializer**: MCP SDK serializes tool return values with `toolJsonOptions` = `JsonSerializerDefaults.Web` (camelCase), `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` (Hindi/Gujarati not `\uXXXX`-escaped), `JsonStringEnumConverter` (`Program.cs:411-418`). Tools return anonymous objects or records (e.g. `TransactionPage<T>`, `KnowledgeSearchResult`, `CatalogLookupResult`, `QuoteEstimate`).
- **Client side (chat)**: `McpToolGateway.CallToolAsync` concatenates `TextContentBlock` texts; empty ⇒ `{"ok":true|false}`; `McpException` ⇒ `IsError=true, Text=message` (`McpToolGateway.cs:176-199`; DTOs `clinqetshared/DTOs/AI/McpGatewayModels.cs:3-16`). `McpAIService` hands `result.Text` back to the model verbatim, or `{error}` JSON (`McpAIService.cs:634-649`).
- **Size caps**: `TransactionsMaxPageSize=25` (validated ≤100; `Program.cs:99`); catalog `LookupMaxResults=5`, `LookupTooBroadThreshold=8`, `LookupSummaryMaxChars=160` (`appsettings.json:78-80`; applied `ProviderCatalogSearchService.cs:488,530,792`); knowledge `RetrievalTopK=8`, `RetrievalMaxTokens=3000` → char budget `×4 − envelope` (`ProviderKnowledgeSearchService.cs:634`), `RetrievalPerDocCap=6`, `RetrievalOverviewTopK=3` (`appsettings.json:100-106`); `send_material_info` `MaxPassagesPerMaterialSend=4`, `MaxMaterialSendChars=12000`, `Images.MaxImagesPerSend=4` (`:113-118`); embedded profile bounds `InstructionsMaxServiceDescriptionChars/MaxOffers/MaxServiceAreas` (`RealtimeSessionPayloadBuilder.cs:687,705-708`). `McpServerSettings.SearchMaxPageSize/SearchDefaultPageSize/SearchDescriptionMaxChars` (`McpServerSettings.cs:63-65`; `appsettings.json:194-196`) — **no reader anywhere** (grep of `clinqetmcp`, `clinqetinfrastructure`, `clinqetcore`, `clinqetshared`, `clinqetapi`, `clinqetfuncations` `*.cs`/`*.json` returns only the class and the appsettings lines): orphan settings left from the deleted `search_services` tool.
- **Truncation/"data not throw" convention**: communicable outcomes are returned as objects with a `note`/`message` the model must speak (e.g. `BookingTools.cs:1360-1380,1350-1358`, `VerificationTools.cs:105-107`, `Tools/VoiceSendChannelResolver.cs:62-99`); genuine faults throw `McpException`; unexpected exceptions become classified guidance (`McpToolGuard.BuildFailureGuidance` `:124-138`).
- **Localization**: tool output is **model-facing English, hardcoded** (every `note` string above). The only `ILocalizationService` use inside tools is `BookingTools.UnlistedItemNote` resolving `Voice_UnlistedItemNote`/`PDF_ServiceProvider` with `"en"` because entity PDFs are English (`:1544-1551`). The MCP registers `LocalizationService` (`Program.cs:195`; `Localization` section `appsettings.json:270-274`) chiefly for the OTP email template path.
- **PII masking** in Customer scope: `CallerMasking` (`Security/CallerMasking.cs:9-48`) on `find_booking*` (`BookingTools.cs:1390-1394`); Partner-scope `get_booking`/`get_quote` are unmasked by design (`PartnerTransactionTools.cs:19`).
- **"Tail-appended params" convention** (memory `service-name-resolution-and-knowledge-quotes-2026-08-25.md:39-41`): unit tests invoke tool methods **positionally**, so a new parameter must be appended after every existing one (inserting mid-signature silently rebinds `notes`→`serviceName`). Visible in code: `request_booking` gained `serviceName`, `priceEstimate` after `updateBookingNumber` (`BookingTools.cs:303-305`); `send_quote` `serviceName`, `price` last (`:809-810`); `create_booking`/`create_quote` likewise (`PartnerTransactionTools.cs:129-130,248-249`).

### 2.5 Rate limiting, audit, metering, error handling

- **Rate limiter** `RateLimiting/McpToolRateLimiter.cs`: per-`businessId` bucket in a `ConcurrentDictionary` (in-process — **per MCP instance, not distributed**) (`:30`); fixed window `RequestsPerWindow`/`WindowMinutes` + `MaxConcurrentToolCallsPerBusiness` (`:44-87`; settings `McpServerSettings.cs:69-75`, appsettings `:215-220` = 60/1/4); `Release` on completion (`:89-98`); idle-bucket reaper never removes in-flight buckets (`:100-119`). **3.2 Options for a provider-JWT-authenticated path that leaves the call-token path untouched — facts about each**

*Option A — reuse the existing gateway as-is (no MCP change).* The API keeps minting Partner-scope `chat-` tokens; add the needed read tools (e.g. `search_knowledge`) to `Mcp:ChatToolAllowlist`. Facts: `search_knowledge`/`answer_catalog_question` are deliberately off the list and pinned (`ChatToolAllowlistConventionTests.cs:50`) — a config-array change must replace the whole array (`McpServerSettings.cs:48`) and update the class default + both repos' appsettings + both convention tests. The session is business-wide Partner scope (§2.8). Each chat request costs one binding upsert + one delete + `tools/list` (cached) + N tool calls + N `McpAudit` writes (`McpToolGateway.cs:71-83,136-148`; `McpToolGuard.cs:141-166`). Per-call counters (`CatalogLookupCount` ≤8 etc.) reset every request because every request is a new "call". Voice-shaped English `note` text rides every result (§2.4). The MCP's rate limit is per business per MCP instance (§2.5). Send/verify tools stay impossible from chat by construction (DR-10).

*Option B — call the same infrastructure services in-process in the API (no MCP involvement).* Facts: the services above are library classes in `clinqetinfrastructure`; the Functions host already composes `IProviderCatalogSearch` + `ICatalogAlarm` + `CatalogSearchDependencies` (`Functions Program.cs:456-461`) and `IFullProviderContextService` (`:451`), proving they run outside the MCP. Authorization could then be evaluated by the API's own pipeline (`[RequiresPermission]`, `ITenantContextAccessor`) per tool/intent before any repository call — the MCP cannot do this (no SQL, no member identity). Nothing in the call-token path is touched. Costs that do not apply: binding docs, `McpAudit` rows, MCP rate limits, HTTP hop. Costs that must be re-created if wanted: per-tool audit, per-business caps, the curated tool descriptions.

*Option C — a new MCP channel for provider JWTs.* Facts: `McpChannelAuthMiddleware` accepts only the secret path + (per-call bearer + binding) or (`X-Internal-Api-Key` for three fixed routes) (`:29-33,99-127`); the MCP has no JWT-bearer package, no Identity signing-key config, no SQL to check membership/permissions. Any provider-JWT acceptance means editing the shared gate and adding claims/permission evaluation to a Cosmos-only host — the opposite of "without touching the call-token path".

*Option D — S2S pattern (API validates the JWT + permissions, calls MCP with `X-Internal-Api-Key` and `businessId`).* Facts: this pattern exists for `active-calls`/`provider-join`/`warm-context` (`Program.cs:591-762`; `VoiceLiveCallClient.cs`), but those are plain minimal-API endpoints — **not MCP tools**: no `McpToolGuard`, no audit, no rate limit, no `CallContext` (`McpChannelAuthMiddleware.cs:380` test name says "WithoutContext"). Reusing it for search would mean new endpoints in the MCP, not tool reuse.

*Option E — richer token/binding (member id + permission snapshot).* Facts: would add fields to `VoiceCallSession` (a Cosmos entity → CLAUDE.md §0.7 owner approval) and/or claims to `VoiceCallTokenClaims`, plus a permission check in `McpToolGuard`/tools, and the API would have to compute and mint the snapshot (it has `TenantContext`). The voice minters (`VoiceCallControlFunction`, `PlivoVoiceCallControlFunction`, `RealtimeCallWebhookFunction`) would be unaffected only if the new fields are optional and the guard treats their absence as today's behaviour.

**3.3 Hard facts that constrain any option**
- The phone assistant's inability to answer "how many bookings do I have" rests on: Customer-scope token (minted only by the Functions host), `partnerOnly` refusal in `McpToolGuard`, `get_provider_context` public subset, the Scope-C `allowed_tools`, and the prompt. None of these depends on how the API authenticates its own users. Adding an API-side path (A/B/D/E) does not widen the caller's surface as long as the Functions minters keep `VoiceCallScope.Customer` (`VoiceCallControlFunction.cs:1491`, `PlivoVoiceCallControlFunction.cs:767`).
- `search_knowledge` is voice-shaped: the description demands an **English** query (`KnowledgeTools.cs:87`), and results carry caller-facing `Note` text (`:475-481`) and `IncludeRefs` for material sending. Its retrieval budget is `Voice:Knowledge:*`.
- MCP deployment is per voice stamp only (`ca`, `in`); any stamp without an MCP has `Mcp:PublicUrl` empty and chat runs toolless (`McpAIService.cs:164-168`; `McpStartupGuard.cs:3-5`).

## 4. Gaps / risks / open questions

1. **Authorization granularity**: a chat session grants whole-business Partner scope for any member with `ai.assistant.use` (§2.7-2.8); `get_booking` returns unmasked customer email/phone (`PartnerTransactionTools.cs:393-398`). For role-aware "how many quotes did Gaurav send", the MCP has no member identity, no permission data, no SQL — enforcement must live in the API or requires Option E (schema + claim change, §0.7).
2. **Committed key material**: `clinqetmcp/Clinqet.Mcp/appsettings.json` contains literal Cosmos (`:35`), Service Bus (`:55`), AI Foundry (`:155,228`), `Mcp.TokenSigningKey`/`InternalApiKey` (`:175-176`), Telnyx (`:301`), 2Factor (`:312`), WhatsApp (`:322`), ACS (`:355`) values; `appsettings.ca.json`/`.in.json` likewise; the API's `appsettings.json` carries the same `Mcp` key/path (`:2039-2041`). CLAUDE.md §19 requires placeholders/KV refs. Prod is protected by the placeholder guard only for `SecretPath`/`TokenSigningKey` (`Program.cs:105-121`).
3. **Rate limiting is per instance** (`McpToolRateLimiter.cs:30`), not distributed; `active-calls` aggregation exists precisely because sockets are instance-pinned (`Program.cs:604-606`).
4. **Audit is write-only**: `IMcpAuditRepository` has no read/query (`:5-8`); ProviderData has no index path for `toolName`/`callId` (`CosmosContainerPolicies.cs:12-40` shows the included paths) — reading audit trails would need a new query + index (§0.7/§3.11).
5. **Orphan settings (CLAUDE.md §4 "no orphaned settings")**: `McpServerSettings.SearchMaxPageSize/SearchDefaultPageSize/SearchDescriptionMaxChars` (`clinqetshared/Models/McpServerSettings.cs:63-65`, `clinqetmcp/Clinqet.Mcp/appsettings.json:194-196`) have **no reader in any repo** (grep, `*.cs` + `*.json`, bin/obj excluded). `search_services` was deleted 2026-07-28 (SKILL `2901`) and its caps were left behind. Not part of this brief to fix; flagged for the owner.
6. **`ChatToolSessions` prefix is the only chat discriminator** (`ChatToolSessions.cs:8-11`); the guard trusts the call id string. A voice minter can never produce it (carrier UUIDs), but any future minter must not either.
7. **Two hosts build the first prompt** (`RealtimeSessionPayloadBuilder` in Functions and in the MCP for Plivo) and two hosts compose `IFullProviderContextService` — any provider-search change to the context shape must stay correct in both (SKILL `4295-4298`).
8. **SKILL drift** (11 items, §2.10) — the census (30/29 vs 33 tools, 9 vs 10 classes), the container of the binding doc, and the "chat MCP is in-process" note would mislead a design session.
9. **Open questions for the owner**: (a) Should provider search run tool calls through the MCP (Option A) or in-process in the API (Option B)? The deciding facts are permission enforcement (API-only) and cost per request (binding + audit writes per turn). (b) Is `search_knowledge` acceptable on the chat allowlist given its English-query/voice notes, or is a provider-facing retrieval wrapper over `IProviderKnowledgeSearch` wanted? (c) Is the `chat-` 15-minute Partner token an acceptable blast radius for team members with limited roles? (d) IN stamp: the API's `appsettings.in.json` points at `clinket-mcp-in-v4-dev` — confirm the IN MCP is live before assuming chat tools work there.
10. **Voice-shaped result contracts**: every tool result carries a spoken-`Note` (`KnowledgeSearchModels.cs:22-29`, `VoiceCatalogModels.cs:18-30`) and `find_services`/`search_knowledge` spend a per-"call" allowance stored on the binding doc (`Tools/CatalogLookupAllowance.cs:11-35`). Reusing these tools verbatim for a provider UI means the model is told what to *say to a caller*; a provider-facing wrapper or a different prompt would be needed to change that register. (All earlier `(pending verification)` items in this document are now closed: API host DI (§3.1), MCP env keys (§2.11), pinned census (§2.3), context/result shapes (§2.3), `McpService` role (§2.7), orphan `Search*` settings (§2.4/#5).)
