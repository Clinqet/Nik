## 2. THE FIVE FINDINGS THAT MATTERED MOST

### 2.1 ‼️ The money symbol came from the business's ADDRESS, not the row's currency

`SearchRefundRequestsTool` resolved the symbol through `ICurrencyService.GetCurrencySymbolAsync`, which
resolves the provider's **primary-address country first** and only falls back to the currency code. And
`BookingDisputeService.ParseCurrency` **defaults to USD** when a booking payment carries no currency — so
that row exists. An Indian business with one such dispute rendered **`₹50.00`** for a fifty-dollar figure,
on the tool whose own header calls it the strictest on the surface, with the payload ordering the model to
quote the string character for character.

My first fix — one lookup per distinct currency — was **also wrong**, and the audit said so: keying by
currency buys nothing when the lookup ignores the key. **Fixed properly:** `ICurrencyService` gained a pure
`GetCurrencySymbol(currencyCode)` — no address, no I/O, no `CancellationToken` needed — and the tool reads
each row's own currency. Three unit tests pin `₹4,500.00`, `₹12,345.67` and `¥5,000`.

### 2.2 ‼️ A provider's deliberate tap could be silently discarded, leaving the file team-wide

The clients skipped the write when the tap matched the open document. **That document is a snapshot.** The
list only refreshes while something is processing, so on a settled page it can be as old as the last
navigation. Interleaving, no race required: the owner restricts a file on their phone; thirty minutes later
the laptop — never refreshed — opens the same file, sees the stale "Only certain roles", and the owner taps
it to confirm. `sameAudience` returns true against the stale snapshot, **no request is sent**, the screen
shows a restriction that is not there, and the file stays findable by the whole team.

**Fixed by deleting the rule from both twins.** The server does the same comparison against the CURRENT row
and costs no write when it matches — that is the only place it is safe. Three more failures fell out of the
same change:

- **a poll already in flight** could land after the write with the pre-write body and revert the row mark;
- **a write that COMMITTED but whose response was lost** (axios timeout, backgrounded app) reverted the box
  while the file really had changed — permanently, because nothing re-read it;
- **a failed write was silent** if the dialog closed before it settled.

Both apps now **reconcile from the server after every write, success or failure**, and both toast on
failure. `knowledgeGuards.test.js` pins the two reconcile calls; the mobile guard pins them too.

### 2.3 ‼️ Both apps printed raw internal role keys to providers, in every language

`nameOf` fell back to the bare `roleKey`, and the roles were fetched only in the editable branch (web) or
only on tapping the picker (mobile). The skeptic confirmed one site as **everyday reachable**: open a
restricted file's editor on the phone and the "Who can find it" field reads **`finance, operations_manager`**
until the field is tapped — snake_case English to a Gujarati- or Hindi-speaking provider, which §0.20 bans
outright.

**Fixed three ways at once:** the roles are fetched whenever a NAME is about to be drawn (including the
read-only summary, which never fetched at all); no name is drawn until the catalogue is ready; and an
unknown key is now **dropped, never printed** — because killing the fallback alone just relocates the leak.

### 2.4 ‼️ The two "always finds everything" role keys were a client copy no test could ever check

Both twins hardcoded `["primary_owner", "administrator"]` to decide which roles to leave out of the picker.
§0.17 forbids a client test from reading `TenancyRoleCatalogDefinition`, so **nothing could ever have caught
a rename** — and the failure direction is the bad one: the picker would offer that role, the provider would
untick it, and the screen would state a restriction the server does not enforce.

**Fixed at the source.** `BusinessRoleAssignmentDto` gained `AlwaysHasFullAccess`, derived in-memory from
the catalogue exactly as `Access` already is, and **both twins deleted their copy**. A test now proves a
FUTURE always-finds role is left out *without being told its key*.

### 2.5 ‼️ Two comments asserted an invariant the code does not implement

`KnowledgeSearchAudienceConverter` said an unrecognised audience value resolves to "Roles **with no keys** …
the identical decision `ListSearchVisibleDocIdsAsync` makes". It does not: a converter sees one property, so
the row's `searchAudienceRoleKeys` survives, and the point-read behind the document page would honour them
while the search sweep excludes them — **the wider answer, on the surface whose whole job is to agree with
retrieval.** `KnowledgeDocument` repeated the claim.

The skeptic **confirmed the divergence and confirmed it is unreachable today** (the enum has exactly two
members and the only writer sets keys solely beside `Roles`), and found a **worse** consequence nobody had
named: the converter is **lossy on round-trip** — an old host reading a future value parses it to `Roles`
and writes `"Roles"` back, destroying the provider's choice permanently.

**Both comments are corrected to say what the code actually does**, and the whole thing is carried to P5
with the cost stated: closing it needs the RAW value preserved on the row, i.e. a new Cosmos field ⇒ §0.7.
A sentinel enum member would make the round-trip loss worse, and the correction says so.

## 6. CLAIMS THAT DID NOT SURVIVE THE SKEPTIC PASS

1. **"An unknown authorization snapshot shows the owner a refusal."** REFUTED. `CapabilityGate` /
   `SurfaceGate` withhold the whole page while `access === null`, so the box cannot render in that window.
   `readonly` IS reachable — by a mid-session demotion while the editor is open, where the copy is correct.
   The `accessKnown` fix stands on the landmine argument, not on a live bug.
2. **"The mobile roles list overflows today."** REFUTED for today: 8 rows fit a 360×640 screen by 2–20 px.
   CONFIRMED as latent with no margin — a 9th role, OS font scaling, or a 3-line hint pushes rows off the
   screen entirely, and RN's `flexShrink: 0` means they do not clip-and-scroll, they lay out past the edge.
   Fixed rather than left to a user's font-size setting.
3. **"A third audience value could leak a document today."** REFUTED as reachable, CONFIRMED as a code
   divergence and two false comments — see §2.5.
4. ‼️ **"`role.alwaysHasFullAccess !== true` is fail-OPEN and should be `!== false`, to match the house
   posture."** The observation is CORRECT — an absent field makes a role tickable, so against an API build
   predating the field the picker would offer `administrator`, the provider would untick it, and they would
   believe an administrator had been shut out when they had not. **The proposed fix is REJECTED, and the
   reasoning matters:** "unknown" is the *same value* for a normal role and an always-finds role, so
   `!== false` cannot refuse the one without refusing the other — it would **empty the picker for every
   ordinary role** and break the feature outright to defend against a state a consistent deployment cannot
   reach (`AlwaysHasFullAccess` is a non-nullable `bool`, so System.Text.Json always emits it). Contorting
   the client rule is the wrong lever. **What is real is a deployment-ordering constraint** — these are
   separate repos, so neither app may ship ahead of the API that adds the field. Recorded as its own line in
   P5's deploy checklist (`PHASE-5-PROMPT.md` §3.4) rather than papered over in code.

## 9. ‼️ DEFECTS IN CODE THIS PHASE NEVER TOUCHED — reported, not adopted

These are real and outside P4. Every one is carried to P5 with its evidence.

1. ‼️ **A duplicate-content upload silently discards the provider's per-file choices — including "don't send
   to callers" — and renames an unrelated document. Reachable today.** When the bytes match an existing Ready
   document, `RefreshHashTwinAsync` copies **only `DocName`** onto the twin and deletes the incoming row. The
   type, the linked offerings and the caller switch the provider just chose are gone; no failure reason is
   set and no notice is dispatched, so it reads as a clean success. A provider who said "do not send this to
   callers" keeps a file that is still sendable.
2. ‼️ **Both provider refund surfaces divide minor units by 100 unconditionally**, so a ¥5,000 refund renders
   **¥50** on the page and the mobile screen while Ask Clinket now says ¥5,000 — and the platform has **four
   disagreeing definitions** of which currencies are zero-decimal, plus one app with no exponent helper at
   all. Latent only because today's live currencies are all 2-decimal.
3. **`list_customers` reads the ENTIRE customer partition on every call** and filters `nameContains` in
   memory — at 900 customers that is 9 sequential Cosmos round trips to hand 10 rows to the model, and the
   file's own comment claims the opposite.
4. **A timed-out audience read is reported as FAILED and the lookup-timeout alarm never fires** — the catch
   has no `OperationCanceledException` exemption, so operations lose the alarm for the slowest read on the path.
5. **Dead `excluded` counter** in the visibility sweep (`_ = excluded;`), which removes the only operator
   signal for how much of a library was withheld.
6. **`businessRoleCatalogParity.test.js` reads a peer repo at describe-callback scope**, which §0.17
   documents as still executing when skipped — so in CI it throws ENOENT and fails rather than reporting
   Skipped. P4's own cross-repo test gets this right.
7. ‼️ **Real Azure credentials are committed and tracked** in the Functions repo's `local.settings.json` (a
   storage account key, a Service Bus send-listen key, an App Insights key). §4/§19 say that file is
   gitignored and local-only. **This needs key rotation, not just a `.gitignore` line.** No value is
   reproduced here or anywhere in this programme's files.
8. **`MaxTotalMediaBytes` is declared in the Functions appsettings only**, while **both** hosts register
   `KnowledgeDocumentParser` (`Clinqet.API/Program.cs:861`, `Clinqet.Communications/Program.cs:803`) and both
   bind `Voice:Knowledge`. The API therefore falls back to the options-class default `268_435_456`, which
